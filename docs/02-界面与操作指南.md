## 1.1 侧边栏「操作」视图

不想每次都去命令面板，就用这个视图 —— 每一项都是一次点击：

```
操作
├─ 阅读路线（从 main 开始）    ← 新：一条有序的阅读路径
├─ 从光标处开始读             ← 起点换成光标所在的函数（库项目 / 从中间起头）
├─ 泳道图（控制权在文件间的流动） ← 每行一个文件，橙色箭头 = 换文件
├─ 起点回到 main              ← 只在起点被改过时出现
├─ 查看依赖图（当前文件）      ← 最常用
├─ 查看依赖图（当前符号）
├─ 全局架构视图
├─ 重建索引（全量）            ← 右侧显示当前精度：精确 / 部分精确 / 近似
├─ 取消索引
├─ 清理索引缓存
├─ 导出依赖数据（JSON）
├─ 导出依赖图
├─ 界面语言                    ← 展开可选：跟随 VS Code / 中文 / English
├─ 如何生成 compile_commands.json
├─ 为什么是近似？              ← 精度诊断：找没找到编译数据库、下一步做什么
└─ 使用文档
```

「重建索引」右侧会直接附上当前整体精度，不用开面板就能判断结果可不可信。

视图标题栏还有两个快捷按钮：⟳ 重建索引、$(type-hierarchy) 查看依赖图。

> 「起点回到 main」是**动态**的：只有你真的改过起点才出现（VS Code 上下文键
> `depscan.routeCustomStart`），否则这一行只是噪音。

## 1.1.1 侧边栏「阅读路线」视图

打开一个大项目，真正的问题不是「有哪些依赖」，而是**从哪读起**。这个视图给的就是这条路径：

```
起点：main（自动识别，src/main.cpp）
路线是「阅读建议」，不是精确调用栈：调用边按名字消解，标注 ⚠ 的步骤请自行判断。
已折叠 2 个琐碎步骤（纯转发 / 小函数）—— 点标题栏的「降噪」按钮可以展开看全部。
有 1 步存在同名定义，展开「候选」可以自行核对。

#1 main                     src/main.cpp:6
  #2 Application::start     src/app/application.cpp:9
    #3 config                include/demo/config.h:24
    #4 Engine::run           src/core/engine.cpp:27
      #6 trim                src/util/string_utils.cpp:7
      #7 Registry::add       src/core/registry.cpp:8
      #8 Engine::describe    src/core/engine.cpp:23
        #10 join             src/util/string_utils.cpp:30
        #11 split            src/util/string_utils.cpp:15
      #9 ⚠ Base::describe    src/core/base.h:25
         └ 候选（另有 1 个同名定义）
             ✓ func:demo::Base::describe（当前）   src/core/base.h:25
               func:demo::Engine::describe         src/core/engine.cpp:23
    #5 Panel::render         src/ui/panel.cpp:13
✓ 路线已完整生成
```

上面这段里步号是不连续的（`#1` 后面直接是 `#2 Application::start`），因为**降噪默认开着**：
`setVerbose`（一行 getter）与 `Registry::size`（一行转发）被折叠了 —— 它们不算「一步」，
但不等于消失：悬停那一步会看到 `已折叠：setVerbose`，视图顶部也会报一共折叠了几个。
想看完整清单就点标题栏的 `$(filter)`。

大项目上再点一下标题栏的 `$(layers)`，就切到**层视图**：第 1 层就是起点，
每层先给一行摘要（几个步骤 / 几个文件），一层里超过 15 个就先给一页 ——
几百行的路线变成几行摘要，想读哪层再展开（层内仍然是阅读顺序）。

**怎么用**

| 操作 | 效果 |
| --- | --- |
| 点任意一步 | 跳到源码对应位置 |
| 展开 / 收起 | 路线本身就是调用树，父子关系一眼看出 |
| 标题栏 `$(arrow-both)` | 切换**广度优先 / 深度优先** |
| 标题栏 `$(file-code)` | 切换**文件级 / 函数级**（文件级只保留每个文件首次进入的那一步） |
| 标题栏 `$(filter)` | **降噪**：折叠 / 展开「纯转发 / 小函数」（默认折叠） |
| 标题栏 `$(layers)` | **层视图**：先给「第几跳、这一跳有多少东西」的摘要，一层太大就分页 |
| 标题栏 `$(list-ordered)` | 重新生成路线 |
| 标题栏 `$(graph)` | 打开**泳道图**（同一个起点、同一批纠偏） |
| 标题栏 `$(target)` | **起点改成光标所在的函数** |
| 标题栏 `$(home)` | 起点回到 main（只在改过起点时出现） |
| 展开 ⚠ 步骤 → **候选** | 这一步有几个同名定义，点一个就改走它；点「当前」那一项 = 撤回 |

路线里**公开接口**那一步会换成接口图标（`$(symbol-interface)`），悬停能看到
「公开接口：include/...:行号」—— 读库时「这一步是不是 API」比「它是什么种类」更需要一眼看见。

**⚠ 和「候选」是什么**

没有 `compile_commands.json` 时，调用边是**按名字**消解的。只要项目里还有**别的同名定义**，
这条边就可能落在了错的那一个上 —— 普通依赖图错一条边只是多一条线，**顺序图错一条边，
后面整条路径都是错的**，所以这里必须显式暴露：

- ⚠ = 这个名字在项目里还有别的定义（悬停看说明）；
- 展开后列出所有同名定义（含文件位置）与**当前用的那一个**；
- 点另一个 = 纠偏，路线立刻按它重算；点「当前」= 撤回，回到引擎原来的判断。

标记多不代表路线没用，只代表「值得核对」——这也正是近似精度的真实代价。

**要知道的几件事**

- **起点默认是 `main`**（依次试 `main / wmain / WinMain / wWinMain / DllMain`）。
  库项目没有 main，把光标放到导出接口上，用「从光标处开始读」。
- **项目外符号默认不进入**（否则走三步就全是 `printf`）。
- **步号在树里不是严格递增的**：树按**调用关系**排，步号是**建议的阅读顺序**。
  广度优先下你要先把上一层读完，所以会出现 `#9 → #12 → #13 → #10`。
  切到深度优先，两者就一致了。
- **步数有上限**（默认 300 步 / 6 层），到底了会显示还有多少个函数没展开，并建议换文件级看个轮廓。
- 起点与纠偏是**会话内**的：重启 VS Code 后回到「自动从 main 开始」。

> 完整设计（两种策略、粒度与层视图、置信度标注、验收标准）见 [07-阅读路线](07-阅读路线.md)。

## 1.1.2 「泳道图」——什么时候值得看

列表看「顺序」，泳道图看「**换文件**」。打开后是一个网格：**横轴是步号，一条泳道一个文件**，
圆点就是每一步，箭头就是「控制权交给谁」。`samples/demo` 上它是 13 步 / 9 条泳道 / 11 次换文件
（状态行会直接报这三个数）。

| 图上元素 | 含义 |
| --- | --- |
| 蓝色圆点 | 一个阅读步骤（圆内是步号） |
| **橙色箭头** | **跨文件**：这一步把控制权交给了另一个文件 —— 这张图的主角 |
| 灰色箭头 | 同一个文件内部的调用 |
| 黄色圆点 | 这一步有同名定义，可能走错边（与列表里的 ⚠ 一致） |
| 向上指的箭头 | 回到了之前读过的文件 |
| 泳道顺序 | **首次进入**的顺序：先碰到的文件在上面 |

面板里能做的事：

| 操作 | 效果 |
| --- | --- |
| **按住左键拖拽** | **平移画布**（光标会变成抓手；这是主要浏览方式） |
| **滚轮** | **以鼠标位置为锚点缩放** —— 指针底下的那一步不会跑掉 |
| 点圆点 | 跳到源码对应位置（拖拽超过 4px 就当作平移，不会误跳） |
| `−` / `+` / 键盘 `+` `-` | 缩放（以视口中心为锚点） |
| 「适应宽度」/ 键盘 `f` | 纵向够看就用整宽；只往小里缩 |
| 「原始大小」/ 键盘 `0` | 回到 100%，并回到阅读起点（左上角） |
| 「导出 SVG」 | 导出**自包含单文件**（样式内联，丢进浏览器就能看） |
| ⟳ | 重新生成（**不会**把你调好的视图打回去） |

手感和依赖图面板一致（同样是滚轮 1.12 倍、同样是拖拽平移），不用记两套。
另外，平移有边界保护：不管怎么拖，内容至少会留 60px 在视口里，不会“拖飞了找不回来”。

右侧图例总是把上面这几条写清楚，不用记。

> 它画的跟侧边栏是**同一条**路线（同一个起点、同一批手工纠偏）——
> 在列表里换了一个候选，图里也是换过之后的顺序。

## 1.2 界面语言

DepScan 的界面文案分两层，**机制不同**，这是 VS Code 平台决定的：

| 层面 | 包含什么 | 由谁决定 | 能否运行期切换 |
| --- | --- | --- | --- |
| **插件文案** | Webview 界面、通知、工具提示、树节点文字、**侧边栏视图标题** | 配置 `depscan.ui.language` | ✅ 改完立即生效 |
| **清单文案** | 命令标题、配置项名称与描述 | VS Code 显示语言（`package.nls*.json`） | ❌ 需切换 VS Code 语言后重启 |

> 视图标题本来是清单文案，但 `TreeView.title` 能在运行期改，所以现在跟着**设置**走 ——
> 不这么做就会出现「界面全中文，只有视图标题是英文」那种半截翻译。
> 命令面板里的命令标题仍然只能跟显示语言（平台行为，绕不过去）。

**怎么切**（三处入口，效果完全一样）：

1. 侧边栏 → DepScan → 操作 → **界面语言**
2. **依赖图工具栏最右侧 → 界面语言**（开着图时不用切窗口）
3. 设置里改 `depscan.ui.language`

```jsonc
{ "depscan.ui.language": "en" }   // auto | zh | en
```

> 想让命令标题也变英文：按 `Ctrl+Shift+P` → `Configure Display Language` → 选 `en` → 重启。
> 只有「中文」和「English」两套清单翻译，其他语言会回落到英文。

> 实现细节：`package.nls.json` 是**英文默认值**，`package.nls.zh-cn.json` 是中文翻译。
> 这样任何未翻译的语言都会拿到英文，而不是中文。

## 2. 依赖图（Graph 视图）

### 画布操作

| 操作 | 效果 |
| --- | --- |
| 拖动节点 | 钉住该节点并移动（松手后解除钉住） |
| 滚轮 | 以光标为锚点缩放 |
| 拖动空白处 | 平移画布 |
| 单击节点 | 选中 + 高亮邻居；开启「点击跳转源码」时同时跳到定义位置 |
| 双击节点 | **展开下一层**（把该节点的邻居合并进当前图） |
| 悬停节点 | 右侧详情面板显示类型 / 文件:行 / 精度 / 出入度 / 签名 |
| 单击空白 | 取消选中，恢复全图色彩 |

### 工具栏

| 控件 | 说明 |
| --- | --- |
| **层级 k** | 以焦点为中心的 BFS 层数（1–6）。k 越大越全，也越慢 |
| **方向** | `双向` / `被谁依赖`（上游）/ `依赖了谁`（下游） |
| **显示项目外符号** | 打开后能看到未解析到定义的符号（标准库、第三方库）。默认关闭以避免噪声 |
| **按目录聚类** | 把同目录的节点折叠成目录节点（LOD 第 1 层），用于全局鸟瞰 |
| **点击跳转源码** | 关闭后单击只做选中，不跳转 |
| **⤢ 适应窗口** | 重新计算缩放，让整张图铺满画布 |
| **⟳ 刷新** | 按当前 k / 方向重新拉取子图 |
| **▦ 全局架构视图** | 按目录聚合的整项目架构图 |
| **PNG / SVG / JSON / DOT / MMD** | 导出 |

### 边的读法

- **颜色**：蓝=包含，绿=调用，橙=继承，紫=类型依赖，灰=符号引用，青=链接
- **实线** = 精确（来自 compile_commands 的真实路径 / CMake 元数据）
- **虚线** = 近似（结构级推断）
- 箭头方向：`A → B` 表示 **A 依赖 B**（A include 了 B / A 调用了 B / A 继承了 B）

### 图例与详情

右侧面板上半是**详情**（悬停/选中时刷新），下半是**图例**（只显示当前图中真实出现的类型，不是固定列表）。

详情里除了「类型 / 文件 / 精度 / 出入依赖」，还会给一行**公开接口**：
那个符号的声明在 `include/`（或 `inc/` `public/` `api/`）下的哪个头文件里。
读库的时候，「定义在哪」与「**声明在哪**」是两件事：前者是实现，后者才是别人能 include 的东西。

树与表格里同名节点会多一个 `公开` 角标（图例里也有它）；
**画布上刻意不画环** —— 大项目里公开面往往是大多数（`include/` 下的每个函数都是），
满屏画环只会把真正的关系滤掉；要看「哪些是 API」去表格里筛更利索。

## 3. 树视图（Tree 视图）

以当前焦点为根：

```
▾ 被谁依赖
  ├─ <includes> main.cpp
  ├─ <calls>    run()
  └─ ...
▾ 依赖了谁
  ├─ <includes> core/base.h
  └─ <calls>    compute()
```

- 每行显示 `<边类型>` 徽标 + 节点名（以及 `公开` 角标、`ext` 角标，有就显示）
- 单击行：选中 + 跳转源码
- 双击行：在图中展开该节点
- 搜索框输入关键字时，树会自动只保留命中的分支（含其祖先）

## 4. 表格视图（Table 视图）

| 列 | 说明 |
| --- | --- |
| 节点 | 名称（前面小圆点表示类型；公开接口会多一个 `公开` 角标） |
| 类型 | 文件 / 函数 / 类 / 枚举 / 变量 / 宏 / 构建目标 |
| 出依赖 | 该节点依赖了多少东西（out-degree） |
| 入依赖 | 有多少东西依赖它（in-degree） |
| 文件 | 定义位置 `路径:行号` |
| 精度 | 精确 / 近似 |

默认按「出依赖 + 入依赖」降序 —— **排在最上面的就是整个子图的枢纽节点**，通常是你最该先读的东西。

搜索框同时过滤树和表格，并会把图里的第一个命中项选中。

## 5. 三视图联动

在任一视图点选一个节点：

- 图中该节点加白色描边，邻居正常着色，非邻居淡化到 18% 透明度
- 树里对应行高亮，并自动展开到该节点所在分支
- 表格里对应行高亮

这是「从架构看到具体代码」的关键：先在图里看形状，再在表格里找枢纽，最后跳到源码。

## 6. 导出

| 格式 | 用途 | 体积 |
| --- | --- | --- |
| **PNG** | 贴进 issue / 文档 / PPT | 中（2 倍分辨率，导出整图而非当前视口） |
| **SVG** | 矢量图，可无损缩放、可二次编辑 | 小 |
| **JSON** | 二次处理（脚本、图算法、导入到其他工具） | 中 |
| **DOT** | Graphviz，适合出版级排版 | 小 |
| **Mermaid** | 直接粘进 Markdown / 文档站 | 小 |

JSON 结构：

```json
{
  "generator": "DepScan",
  "version": "0.1.2",
  "root": "/path/to/project",
  "stats": { "fileCount": 15, "edgeCount": 76, "precision": "approx", "...": "..." },
  "graph": {
    "nodes": [{ "id": "file:src/main.cpp", "kind": "file", "name": "src/main.cpp", "precision": "exact", "...": "..." }],
    "edges": [{ "from": "file:src/main.cpp", "to": "file:src/util/logger.h", "kind": "includes", "line": 3 }]
  }
}
```

节点 `id` 命名规则（稳定、可脚本化）：

```
file:<相对路径>     func:<限定名>      class:<限定名>
enum:<限定名>       var:<限定名>       macro:<宏名>
target:<target 名>  ext:<类型>:<名字>   ← 项目外/未解析符号
```

## 7. 索引、缓存与增量

> 索引完成后会自动跑一次**架构边界检查**，结果进 VS Code 原生的「问题」面板：
> 公开头文件引用了内部实现、目录之间互相 include 成环这两类。点诊断能跳到那一行，
> 开关是 `depscan.checks.enabled`（关掉会把已有诊断一并清掉）。
> 它为什么不报「按目录名猜出来的分层倒挂」，见 [08-架构边界检查](08-架构边界检查.md)。

### 索引流程

```
打开工作区
   ↓ 自动（depscan.index.onStartup）
发现 compile_commands.json → 决定精度
   ↓
文件发现（files.include / exclude 过滤）
   ↓
多线程并行结构解析（threads = CPU 核心数）
   ↓
符号表 → include 解析 → 引用消解 → CMake 链接模型 → 图构建
   ↓
写磁盘缓存（带配置指纹）→ 通知 UI
```

> 编译数据库变化时会**自动全量重新索引**：扩展监听 `**/compile_commands.json`，
> 文件出现 / 变化 / 删除后防抖 800ms 重新扫描，并弹一条「已重新索引，当前精度：…」。
> 所以「先索引、后生成 compile_commands.json」也能自己缓过来。
>
> ⚠ **CMake 的 Visual Studio 生成器永远不产出 `compile_commands.json`**（`CMAKE_EXPORT_COMPILE_COMMANDS`
> 只对 Makefile / Ninja 生成器生效）。这就是「我明明编译了、build 目录也有一堆文件，却还是近似」的头号原因。
> 换成 Ninja 生成器即可，详见 [04-解析与精度说明](04-解析与精度说明.md) 的 FAQ 第 2 条。

### 增量更新（保存文件后自动发生）

```
文件保存 / 新建 / 删除
   ↓ 防抖 400ms
只重解析变化的文件
   ↓
重建图（受影响子图合并回主图）
   ↓
写缓存 → 通知依赖视图与依赖图刷新
```

若正在全量索引，保存事件会被忽略（避免互相干扰）；全量结束后再保存一次即可。

### 缓存

- 默认位置：`<工作区>/.vscode/depscan-cache/index-v1.txt`
- 失效判定：**文件 mtime + size**（变化才重解析，其余直接复用）
- **整体有效性靠配置指纹**：`根目录 + 编译数据库路径/条目数/mtime + include 路径 + 系统 include + 宏 + 文件大小上限`。
  任何一项变化，整份缓存作废并重新解析 —— 这是为了让新生成的 `compile_commands.json`
  能真正改变结果（旧版本的坑：缓存命中后一直沿用旧的「近似」结果）。
- 缓存头部记录项目根路径 —— 换项目自动失效，不会串味
- 想强制冷启动：`DepScan: 清理索引缓存` 或 `DepScan: 重建索引（全量）`

### 面板工具栏的 ⟳ 到底做了什么

1. 先检查编译数据库是否比上次扫描更新（新出现 / mtime 变了 / 换了一份）；
2. 是 → 先全量重扫（精度、包含边、链接边都跟着更新），再取子图；
3. 否 → 只按当前深度 / 方向重新取一次子图。

所以「编译完再点 ⟳ 还是近似」这类旧坑不会再出现。
