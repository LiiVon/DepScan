# 05 · 性能与配置参考

---

## 第一部分：配置项字典

所有配置项前缀为 `depscan.`，可在「设置」界面搜索 `depscan`，或写入 `.vscode/settings.json`（推荐工作区级，可随项目提交）。

### 界面

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.ui.language` | `auto`\|`zh`\|`en` | `auto` | 界面语言。`auto` 跟随 VS Code 显示语言（非英文环境一律显示中文） |

### 引擎

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.engine.path` | string | `""` | 自定义引擎可执行文件路径。留空则按 `engines/<platform>-<arch>/` → 开发态 `engine/build/bin/<Config>/` 依次查找 |

### 索引

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.index.onStartup` | boolean | `true` | 打开工作区后自动在后台建立索引 |
| `depscan.index.autoRebuildOnSave` | boolean | `true` | 保存文件后增量重建受影响子图 |
| `depscan.index.parallelism` | number | `0` | 解析线程数；`0` = 自动（CPU 核心数，上限 64） |
| `depscan.index.maxFiles` | number | `20000` | 单次索引最多扫描的文件数（防止误扫超大目录） |
| `depscan.index.fileSizeLimitKB` | number | `2048` | 超过该大小的文件跳过深度解析（只作为节点存在） |

### 文件范围

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.files.include` | string[] | `["**/*.{c,cc,cpp,cxx,h,hh,hpp,hxx,inl,ipp}"]` | 参与索引的文件 glob |
| `depscan.files.exclude` | string[] | 见下 | 排除 glob |

默认排除：`**/node_modules/**`、`**/.git/**`、`**/build/**`、`**/out/**`、`**/cmake-build-*/**`、`**/.cache/**`

glob 语法：`**` 跨目录、`*` 不跨目录、`?` 单字符、`{a,b,c}` 多选。
以 `**` 结尾的排除项会被用于**目录剪枝**（遍历时直接跳过该目录，大项目提速明显）。

### 编译数据库

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.compile.commandsPath` | string | `""` | compile_commands.json 路径；留空自动发现 |
| `depscan.compile.includePaths` | string[] | `[]` | 额外头文件搜索路径（等价 `-I`），相对项目根 |
| `depscan.compile.systemIncludePaths` | string[] | `[]` | 系统头文件搜索路径（等价 `-isystem`） |
| `depscan.compile.defines` | string[] | `[]` | 额外宏定义（等价 `-D`） |

**自动发现顺序**：`compile_commands.json` → `build/` → `out/` → `cmake-build-debug/` → `cmake-build-release/` → `build/Release/` → `build/Debug/` → 项目内深度 ≤ 4 的递归搜索。

### 依赖类型开关

| 配置项 | 默认 | 关闭的后果 |
| --- | --- | --- |
| `depscan.deps.includes` | `true` | 没有 `includes` 边；架构视图为空 |
| `depscan.deps.calls` | `true` | 没有 `calls` 边；函数级导航失效 |
| `depscan.deps.types` | `true` | 没有 `inherits` / `uses` 边 |
| `depscan.deps.symbols` | `true` | 没有宏 / 全局变量节点与 `refs` 边 |
| `depscan.deps.links` | `true` | 不解析 CMake，没有 `links` 边与 target 节点 |

> 关闭某项会同时减少解析与建图开销，是**最有效的性能开关**（见下文调优）。

### 图与渲染

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.graph.defaultDepth` | number (1–6) | `2` | 依赖图默认层级 k |
| `depscan.graph.direction` | `both`\|`upstream`\|`downstream` | `both` | 默认依赖方向 |
| `depscan.graph.maxNodes` | number | `800` | 单张图最多渲染的节点数 |
| `depscan.graph.clusterByDirectory` | boolean | `true` | 打开面板时默认按目录聚类 |

### 缓存与日志

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `depscan.cache.enabled` | boolean | `true` | 启用磁盘缓存（二次启动秒开） |
| `depscan.cache.directory` | string | `""` | 缓存目录；留空 = `<工作区>/.vscode/depscan-cache` |
| `depscan.log.level` | `off`\|`error`\|`warn`\|`info`\|`debug` | `info` | 输出通道日志级别 |

## 第二部分：性能

### 2.1 实测数据

两个合成工程的实测结果（Windows / MSVC Release / 本机 CPU，`depscan-core --once`）：

| 指标 | 测试 A | 测试 B |
| --- | --- | --- |
| 源文件数 | 6,036 | 6,038 |
| 代码行数 | 108,073 | **1,068,077** |
| 进程墙钟时间（启动+发现+解析+建图+序列化） | 1,136 ms | **1,426 ms** |
| 引擎内部索引耗时 | 380 ms | 423 ms |
| 吞吐（墙钟） | 95 K 行/秒 | **749 K 行/秒** |
| 符号数 | 30,036 | 30,014 |
| 节点 / 边 | 36,073 / 37,023 | 36,053 / 36,003 |
| 未解析引用 | 4,980 | 5,640 |
| 输出 JSON 体积 | 15.1 MB | 15.0 MB |

复现方式：

```bash
npm run stress:gen      # 生成 10 万行合成工程到 stress/
npm run stress          # 扫描并生成 engine/build/stress-report.md
npm run stress:gen:1m   # 生成百万行合成工程到 stress1m/
npm run stress:1m       # 扫描并生成 engine/build/stress-report-1m.md
```

**怎么读这张表（重要）**

1. **代码行数不是瓶颈，文件数与符号数才是。** A 与 B 相差 10 倍行数，但耗时只差 25% —— 因为 B 只是在方法体里增加了语句，文件数、符号数、图规模几乎不变。真实项目的耗时更接近「文件数 × 每文件符号数」。
2. **墙钟时间里有约 750–1000 ms 是"与代码量无关"的固定开销**：进程启动、文件系统遍历、JSON 序列化（15 MB 输出）。A 与 B 的墙钟差值 ≈ 290 ms，就是 96 万行代码的增量解析成本。
3. **合成代码高度重复**（无模板元编程、无深层嵌套、无复杂宏），所以这个吞吐是**上限参考**，真实项目会低一些。
4. **未对峰值内存插桩**，因此不报告内存数字（不给出没有依据的估算）。自行测量：
   - Windows：任务管理器观察 `depscan-core.exe` 的工作集
   - Linux：`/usr/bin/time -v <engine> --once --root <dir>` 看 `Maximum resident set size`

### 2.2 为什么它快

| 手段 | 说明 |
| --- | --- |
| **独立进程** | 解析在 C++ 进程里跑，不占用扩展宿主的 Node 线程，编辑器始终不卡 |
| **多线程并行** | 文件级任务队列 + 原子索引分配，线程数默认 = CPU 核心数 |
| **文件级结果复用** | 每个文件只做一次结构解析，引用消解在全局符号表上做（一次 O(引用数) 遍历） |
| **服务端裁剪** | 图不整张推送，引擎做 k 层 BFS 后只回传子图；预览大项目时网络/内存开销恒定 |
| **磁盘缓存** | 以 `mtime + size` 判定失效，二次启动只重解析变化的文件 |
| **单遍词法** | 注释/字符串剥离与 token 化在一次线性扫描内完成，无回溯 |
| **去重式建图** | 边以 `(from,to,kind)` 为键去重，避免重复符号导致的图爆炸 |

### 2.3 调优清单（按收益排序）

**1. 缩小文件范围（收益最大）**

```jsonc
{
  "depscan.files.exclude": [
    "**/build/**", "**/out/**", "**/_deps/**", "**/third_party/**",
    "**/external/**", "**/vendor/**", "**/cmake-build-*/**", "**/.git/**"
  ]
}
```

第三方代码通常占项目的大头，却几乎不需要阅读。排除它们往往能砍掉 50%+ 的索引时间与 80% 的图噪声。

**2. 关掉不需要的依赖类型**

```jsonc
{ "depscan.deps.symbols": false }   // 只看 include / 调用 / 继承，关闭宏与全局变量图
```

**3. 降低图规模**

```jsonc
// .vscode/settings.json
{ "depscan.graph.defaultDepth": 1, "depscan.graph.maxNodes": 400 }
```

`k = 1` 时只画直接邻居，几乎瞬时；需要更远时在图里双击节点按需展开。

**4. 提高并行度 / 限制并行度**

- 机械硬盘或 IO 受限：`"depscan.index.parallelism": 4`（避免磁盘抖动）
- 大内存多核机器：保持 `0`（自动）即可

**5. 跳过超大文件**

```jsonc
{ "depscan.index.fileSizeLimitKB": 1024 }   // >1MB 的文件跳过深度解析
```

生成代码（`*_pb2.cc`、`moc_*.cpp`、`*.generated.cpp`）动辄数 MB，且几乎不需要阅读。

**6. 关闭自动索引**

```jsonc
{ "depscan.index.onStartup": false }
```

改为手动触发 `DepScan: 重建索引（全量）`。

### 2.4 大仓库的推荐配置模板

```jsonc
// .vscode/settings.json —— 20 万行以上的项目
{
  "depscan.index.onStartup": true,
  "depscan.index.autoRebuildOnSave": true,
  "depscan.index.parallelism": 0,
  "depscan.index.maxFiles": 30000,
  "depscan.index.fileSizeLimitKB": 1024,

  "depscan.files.exclude": [
    "**/build/**", "**/out/**", "**/cmake-build-*/**",
    "**/third_party/**", "**/external/**", "**/_deps/**",
    "**/node_modules/**", "**/.git/**",
    "**/*.pb.cc", "**/*.pb.h", "**/moc_*.cpp"
  ],

  "depscan.compile.commandsPath": "build/compile_commands.json",

  "depscan.graph.defaultDepth": 2,
  "depscan.graph.maxNodes": 600,
  "depscan.graph.clusterByDirectory": true,

  "depscan.cache.enabled": true,
  "depscan.log.level": "warn"
}
```

### 2.5 增量索引做了什么

保存文件后的完整流程（防抖 400ms）：

```
保存 / 新建 / 删除
   ↓
只重解析「变化的文件」（其余从内存中的文件级结果直接复用）
   ↓
重建全局图（O(文件数 + 引用数)，一次线性遍历）
   ↓
写磁盘缓存（mtime + size 更新）
   ↓
通知依赖视图与已打开的依赖图面板刷新
```

`DepScan: 查看依赖图` 面板在你编辑时不会闪：它只在增量更新完成后重新拉取当前焦点的子图。

## 第三部分：故障排查

| 现象 | 排查 |
| --- | --- |
| 状态栏一直 `DepScan` 不动 | 打开「输出 → DepScan」看日志；多为项目内无可索引文件或引擎缺失 |
| `未找到 DepScan 分析引擎可执行文件` | 设置 `depscan.engine.path`；或开发态先跑 `npm run build:core` |
| 引擎反复重启 | 查看日志中的退出码；常见原因是引擎二进制与当前平台不匹配 |
| 索引结果为空 | 执行 `DepScan: 重建索引（全量）`；确认 `files.include` 覆盖你的源码后缀 |
| 结果明显不对 | 先确认精度标识；补上 `compile_commands.json` 后再看 |
| 编辑器卡顿 | 降低 `graph.maxNodes` / `defaultDepth`；排除 `third_party` 等大目录 |
| 想彻底重来 | `DepScan: 清理索引缓存` → 再 `重建索引（全量）` |
| 打开指南 | 命令面板 → `DepScan: 打开 DepScan 使用文档` |
