# 架构边界检查：只报「可证明」的东西

依赖图告诉你「谁连着谁」，但有些连接是**症状**而不是信息。这一份文档讲的是 DepScan
怎么把它们挑出来 —— 以及为什么它刻意**不做**某些看起来更聪明的事。

---

## 1. 两条检查

| 检查 | 诊断 code | 什么时候报 |
| --- | --- | --- |
| **公开头文件引用内部实现** | `depscan.public-api-leak` | `include/`（或 `inc/` `public/` `api/`）下的头文件，引用了非公开文件里的东西 |
| **目录之间成环** | `depscan.directory-cycle` | 两个或更多目录互相 include（依赖图上的强连通分量 ≥ 2） |

两条的共同点是**不需要启发式**：

- 泄漏看的是「公开面 vs 非公开面」的边 —— 事实就是那条 `#include`
- 环是图论算出来的（Tarjan 强连通分量）—— 三个目录绕成环也会被抓到，不是只找「互引对」

在仓库自带的 demo 上，第二条会命中那个故意埋的反向依赖：

```jsonc
// depscan-core --violations --root samples/demo
{
  "violations": [
    { "kind": "directory-cycle", "fromFile": "src/core/registry.h", "fromLine": 9,
      "edgeCount": 3, "dirs": ["src/core", "src/ui"] }
  ],
  "total": 1
}
```

`samples/demo/README.md` 之前写着这条「可在架构视图里人工识别」—— 现在它自动报出来了。

---

## 2. 为什么**不**按目录名猜层次

最常见的做法是按名字猜：「`core` / `base` / `util` 算底层，`app` / `ui` 算上层」，
然后报「底层依赖了上层 = 分层倒挂」。DepScan 刻意没做这件事，原因只有一个：

> 目录名是**约定**，不是**事实**。

换个项目（`lib` / `runtime` / `platform` / `server`）这个规则就全错，而这个检查一旦开始
误报，用户的第一反应不是「我去核对一下」，而是**直接把它关掉** —— 那它连真问题也一起丢了。

所以这里只保留两种「自己能核对」的判定。顺带说：demo 里那个 `core → ui` 也**不是**靠名字
认出来的 —— 它是因为 `ui` 也反过来 include 了 `core`，构成一个真实的环。

---

## 3. 判定细节（都可以自己验）

**公开面**：路径以 `include/`、`inc/`、`public/`、`api/` 开头。这是安装规则最常见的写法，
也是唯一可核对的信号（原因见 [04-解析与精度](04-解析与精度说明.md) §2.6）。

**只认「解析到了项目内文件」的边**：

- 外部符号（`<string>`、系统头文件）不算
- 没解析到的 `#include` 不算

这条取舍是刻意的：**漏报是安全的，误报会让检查被关掉**。反过来说，没有编译数据库时它可能
漏掉一些真实泄漏 —— 想让它更准就配 `depscan.compile.includePaths`（等价 `-I`）。

**同目录内部互相 include 不算**：`src/a.h` 与 `src/b.h` 互相引用在 C++ 里太常见了
（前置声明不够用的时候），这跟「分层」没关系。所以目录图的边是**跨目录**的，
同一目录内部的环会被忽略。

**环的代表边优先取「从头文件出发」的那一条**：头文件引到别的层，会把问题传染给每个包含它的人，
比一个 `.cpp` 里引一下更需要先看。demo 上因此定位到 `src/core/registry.h` 而不是同目录的 `.cpp`。

## 4. 结果落在哪里

### 「问题」面板（默认开着）

索引完成后自动跑一次，结果作为**诊断**发到 VS Code 的「问题」面板：

- 点一下直接跳到那一行
- 能按文件分组、按 `depscan.` 前缀筛选
- 增量保存后**整份重算**：增量只改了少数文件，但「目录成环」是全局属性 ——
  只想更新受影响的那几条，很容易留下幽灵（边没了、诊断还在）

级别统一是 **warning**，不是 error：这两件事对**本仓库**编译都没影响（在本机那个内部头
找得到），报成红色等于替用户判断「你必须改架构」。想更严的人可以走下面的 CI 出口。

开关：`depscan.checks.enabled`（默认 `true`）。关掉时会把已有诊断**清掉** ——
否则面板里会留着一堆再也不会更新的告警。

### 命令

侧边栏「操作」→ **架构边界检查**（或命令面板 `DepScan: 架构边界检查`）：
当场再查一遍，然后给你一句话结论 ——

```
架构边界检查：1 处 —— 公开面泄漏 0 处 / 目录循环 1 处。详见「问题」面板，点一下能跳到那一行。
```

被截断时会**如实说**（`共 N 处，这里只列出了前 M 处`）—— 「只列了 500 个」与「一共就 500 个」
是两件事。

### CI（不看 VS Code 也能用）

```bash
depscan-core --once --violations --root .
# 有违规 → 退出码 1；干净 → 0
```

```yaml
# GitHub Actions 片段
- run: ./engine/build/bin/Release/depscan-core --once --violations --root . --pretty
```

## 5. 实测

```
samples/demo     → {"violations":[{"kind":"directory-cycle", ...}],"total":1}   退出码 1
samples/libdemo  → {"violations":[],"total":0}                                  退出码 0
```

`libdemo` 那个干净结果同样重要：它是个**很小但结构完整**的库（公开头文件、内部头、
匿名命名空间），检查在它身上一条都不报 —— 误报是这类功能的死因，所以测试里专门钉了这条。

## 6. 已知边界（说清楚不做什么）

- **需要 include 能解析**：没有编译数据库时，`#include "internal.h"` 这种靠私有 `-I` 才能
  解析的写法会漏报。配 `depscan.compile.includePaths` 即可。
- **不判断设计意图**：「这个 API 该不该公开」「这个函数该不该在头文件里」是人的决定，
  工具只报**结构上可证明**的边界问题。
- **只到目录粒度**：文件级的环（`a.h` ⇄ `b.h`）不报 —— C++ 里它常见且往往是有意为之。
- **不代替 linter**：这里的检查源是「依赖图」，不是 AST 级的代码规范（那是 clang-tidy 的地盘）。
