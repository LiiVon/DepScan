# 03 · 如何用 DepScan 学习一个陌生项目

> 这一篇不讲功能，只讲**套路**。每条都是可以直接照做的操作序列。

前置：项目已索引完成（状态栏显示 `DepScan N 文件 / M 依赖`）。本文用仓库自带的 `samples/demo` 做演示——它只有 15 个文件，但完整包含了一个中小型 C++ 项目的全部结构要素。

---

## 套路 0：先看骨架，不看代码（30 秒）

**做什么**：打开依赖图 → 点击工具栏 **▦ 全局架构视图**。

**看到什么**：按目录聚合的方块图。

在 `samples/demo` 上你会看到：

```
app/  ──► core/
ui/   ──► core/
core/ ──► util/
core/ ──► ui/     ← 注意这条
```

**怎么读**：箭头是「依赖」方向。

- `app → core → util` 是正常的分层（上层依赖下层）
- `core → ui` 是**倒挂**：底层 `core` 依赖了上层 `ui`。这是典型的分层违规，会让模块变得无法独立测试、无法复用

**收获**：30 秒内你知道了「这个项目的模块划分」和「哪里可能是坑」。

> 更细的方法：打开 `按目录聚类` + `显示项目外符号`，可以同时看到「项目内模块」和「依赖了多少外部库」。

---

## 套路 1：从入口出发，看阅读路线

**场景**：你想知道「程序启动后到底干了什么」。

**最快做法**：侧边栏 → **DepScan → 阅读路线**。它已经把从 `main` 出发的那条线排好了：

```
#1 main ─► #2 Application::start ─► #3 config / #4 Engine::run / #5 Panel::render
                                          └─ #6 trim / #7 Registry::add / #8 Engine::describe
```

点一步跳一处，顺着号往下读就行。**先看骨架就用广度优先，想追一条具体流程就切深度优先。**
大项目里 `main` 不是你想要的起点（或者在平台相关文件里），用「**从光标处开始读**」换成
你正看的那个函数。

> 步号里跳掉的那些（`setVerbose`、`Registry::size`）是默认开着的**降噪**折叠掉的
> 一行 getter —— 悬停那一步能看到它们。想全看就点标题栏的 `$(filter)`。

**读一个库（没有 `main`）时**：路线视图会直接列出**起点候选**（公开接口优先），
点一个就从那里开始读；路线里**公开接口**那一步是接口图标，悬停能看到声明在哪个头文件 ——
读库时先把「别人会调什么」和「内部怎么实现」分开，剩下的才不混乱。

**想看「关系」而不是「顺序」时**，再用图：

1. 打开 `src/main.cpp` → 右键 → **查看依赖图**（`k = 2`）
2. 图中找到 `main` 节点（绿色函数）→ **双击** 展开下一层
3. 只有一条调用边 → 沿它继续双击，直到出现分叉
4. 每次展开后，用 **表格视图** 看哪个节点的「入依赖」最高 —— 那就是主干汇聚点

在 demo 上：

```
main ──► Application::start ──► Engine::run ──► Registry::add
                                        └──► logLine
```

**为什么这样高效**：你不用打开 15 个文件，只需要打开「链上被调到的那 4 个」。

**进阶**：切换到 **方向 = 依赖了谁**，把 k 提到 3，就能看到完整主干；再切回 **被谁依赖** 看谁会回过来调用它（在 demo 里 `Engine::run` 还间接通过 `Registry::add → Panel::render` 回到 UI）。

> **阅读路线上标 ⚠ 的步骤别跳过**：那表示这个名字在项目里还有别的定义，
> 没有编译数据库时调用边是按名字消解的，所以那一步可能是错的。
> 展开「候选」看一眼真伪，或者干脆补一份 `compile_commands.json`（见[套路 0](#套路-0先看骨架不看代码30-秒) 后面的说明）。

## 套路 2：用 include 图定位模块边界

**场景**：项目没有文档，你想知道「哪些头文件是公共契约，哪些是内部实现」。

**步骤**：

1. 打开依赖图 → 选择 **方向 = 被谁依赖**
2. 把 **k 调到 3**，节点类型只看文件（表格里按「入依赖」排序）
3. **入依赖最高的头文件 = 公共契约**

在 demo 上：`src/util/logger.h` 出现在几乎所有文件的依赖里 —— 它是被滥用成公共设施的工具头。

再配合一条经验规则：

| 现象 | 含义 |
| --- | --- |
| 头文件被大量文件 include | 公共契约 / 事实上的核心接口 |
| 头文件只被 1–2 个 `.cpp` include | 内部实现，改它风险低 |
| 两个头文件互相 include（图里出现**双向箭头**） | 循环依赖，编译慢、易碎 |

在 demo 里 `core/engine.h` ↔ `core/registry.h` 就是**循环包含**——这也是一个刻意埋下的示例。

**动手改成不含循环的版本**（这是很好的练手）：
把 `Registry` 里 `#include "core/engine.h"` 删掉，改成前向声明 `class Engine;`。
保存后 DepScan 会自动增量更新，你再刷新依赖图，会发现那对双向箭头消失了。

## 套路 3：用继承图理解架构骨架

**场景**：项目里有一堆 `XxxServiceImpl`、`XxxHandler`，你想知道它们的公共抽象是什么。

**步骤**：

1. 打开任意一个具体类的 `.h` → **查看依赖图**
2. 图里 **橙色节点** = 类。找指向它的 `继承` 边（橙色箭头）
3. 沿继承边向上（方向 = `依赖了谁`）走到基类
4. 在基类上切 **方向 = 被谁依赖**，看它有多少派生实现

在 demo 上：`Engine : public Base`，而 `Base` 声明了 `virtual reset()/describe()`。

**收获**：一分钟内拿到了「抽象接口 → 实现者」的完整清单。这通常就是架构的骨架。

**进阶**：`uses` 类型的边（紫色）表示「成员 / 参数 / 局部变量的类型依赖」，它告诉你**类的组合关系**。继承是 `is-a`，`uses` 是 `has-a`——两条边一起看，才是完整的对象图。

## 套路 4：用交叉引用找实现、找落点

**场景**：你看到一行 `logLine(Level::Trace, "registry add");`，想知道 `logLine` 在哪实现、还有谁在用。

**步骤**：

1. 把光标放在 `logLine` 上
2. 命令面板 → **`DepScan: 查看当前符号的依赖图`**
3. 图会以 `func:demo::logLine` 为焦点，**方向 = 被谁依赖** → 所有调用方；**依赖了谁** → 它调用的东西
4. 单击任一节点直接跳源码

**为什么比全局搜索好**：全局搜索会给出一堆注释里的同名文本；DepScan 给的是**经过消解的调用关系**，并且能一眼看出调用方的分布（集中在哪个模块，说明这个函数的职责边界在哪）。

---

## 套路 5（组合拳）：一次完整的「读懂一个模块」

把上面四招按顺序组合：

| 步骤 | 操作 | 目标 |
| --- | --- | --- |
| 1 | ▦ 全局架构视图 | 知道有几个模块、谁依赖谁 |
| 2 | 选一个模块，看它的目录节点邻居 | 找出该模块的入口与出口 |
| 3 | 打开模块入口文件的依赖图（k=2） | 找出它调用的核心函数 |
| 4 | 在核心函数上切「被谁依赖」 | 确认调用链是否收敛 |
| 5 | 表格按入度排序 | 找出模块的枢纽符号 |
| 6 | 逐个跳转枢纽符号的源码 | 只读真正重要的代码 |

**时间预算**：15 分钟。**产出**：一张能画在白板上的模块图 + 一份「该读的文件清单（通常不超过 10 个）」。

## 自检：你现在能回答这些问题吗

对一个你正在读的项目，尝试不看代码回答：

- [ ] 项目有几个模块？谁依赖谁？有没有倒挂？
- [ ] 从 `main` 到「数据处理核心」的调用链是什么？
- [ ] 哪个头文件是最重要的公共契约？改它会影响多少文件？
- [ ] 项目里有几处循环包含？分别在哪？
- [ ] 最"重"的那个类被多少地方依赖？它是不是上帝对象？
- [ ] 有没有构建目标链接了你以为没用的库？

答不上来的，回上面找对应套路再走一遍。

---

## 给学生的一句话

> **依赖图的价值不是「看到全貌」，而是「知道先读哪 5 个文件」。**
> 大项目读不完是常态，读得对才是本事。
