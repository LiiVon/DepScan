# 06 · 发布与版本管理

> 这一篇讲清楚：怎么把 DepScaner 发到 VS Code Marketplace（以及 Open VSX），
> 以及发布这件事里**哪些决定是不可逆的**。

---

## 0. 先记住三件不可逆 / 不可省的事

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | `publisher` ID **首次发布后永久锁定** | 填错只能换新 ID 重新发布，用户和安装量全部清零 |
| 2 | `package.json` 的 `name` 也不能改 | 改了就是一个全新扩展 |
| 3 | 版本号**不能重复发布** | 同一版本发两次会被直接拒绝，改代码必须升版本 |

另外一条容易忽略的：**`vsce publish` 不会跑 `scripts/package.mjs`**。
它只执行 `vscode:prepublish`（= `build:prod`），
所以 `engines/<platform>-<arch>/` 里的引擎二进制不会被刷新 ——
很可能发出一个**没有引擎**、或者**带着上次旧引擎**的包。
这就是为什么本项目提供了 `npm run publish`（先打包再上传）。

还有一条 Windows 特有的：**运行中的 exe 不能被覆盖**。
如果你本地装了 DepScaner 并且它正在跑，`engines/<platform>/depscaner-core.exe` 会被锁住，
`npm run package` 会报 `EBUSY`。
处理：VS Code「扩展」面板里**禁用 DepScaner**（或关掉那个窗口），再打包。
脚本会检测文件内容是否真的变了：没变就跳过复制，不会白白报错。

## 0.1 改名：从 `liivon.depscan` 到 `liivon.depscaner`

产品名从 **DepScan** 改成了 **DepScaner**，而且**扩展 ID（`package.json` 的 `name`）
一起换了** —— 这等于发一个全新的扩展，不是更新。所以要清楚代价与善后：

**代价**

- 旧条目 `liivon.depscan` 不会收到新版本；它的安装量、评分、评论**不会迁移**。
- 装了旧版的用户**必须手动换装**：禁用/卸载旧扩展 → 安装新的。
  如果两个都装着，会**同时注册同名命令**（旧的是 `depscan.*`，新的是 `depscaner.*`，
  其实不会撞车，但侧边栏会出现两个图标，容易混淆）。
- 旧版本的设置项是 `depscan.*`，新版本读 `depscaner.*` —— **配置不会自动继承**，
  用户需要重新设一遍（如果是工作区级 `.vscode/settings.json`，改个前缀就行）。

**善后（建议按顺序做）**

1. 在 `https://marketplace.visualstudio.com/manage` 里把旧的 `liivon.depscan`
   描述改成「已停止维护，请改用 DepScaner」，避免用户继续装旧的。
2. 用同样的发布流程发新 ID（第一次发布会**自动创建**新条目）：
   ```bash
   npm run package            # 产出 depscaner-<version>.vsix（内置引擎）
   npm run publish:win32-x64  # 或 npm run publish（走 CI / 多平台）
   ```
3. 两个 ID 的发布用的是**同一个 Publisher 与同一个 PAT**，不需要重新申请。
4. 如果**同时**要把 GitHub 仓库改名（例如 `LiiVon/DepScan` → `LiiVon/DepScaner`），
   记得同步 `package.json` 里的三处 URL（`repository` / `bugs` / `homepage`）——
   它们目前仍指向 `LiiVon/DepScan`，因为**仓库确实还叫这个名**。
   （`npm run package` 会校验它们：字段指到不存在的仓库会被 vsce 判为错误。）
5. 新 ID 的第一个版本建议直接从 `0.1.1` 起（CHANGELOG 里那条就是），不必开 1.0.0。

> **内部标识没有跟着改**：C++ 命名空间与头文件目录仍是 `depscan/`、CMake 变量仍是
> `DEPS_*`、缓存目录是 `depscaner-cache`。前两个用户看不见，改它们只会给构建添乱；
> 缓存目录会改是因为它是**用户可见路径**（文档与设置项里都写着）。
>
> 改名是批量操作，最容易漏的是**裸词**（`getConfiguration('depscan')`、
> `affectsConfiguration('depscan')`、`package.json` 的 `"name"`）——
> 带分隔符的 `depscan.xxx` 反而好找。`scripts/check-webview.mjs` 里现在有 8 条守卫盯着
> （ID 前缀、命令声明与注册对齐、配置键前缀、以及「配置键是否真被代码读到」）。

## 1. 一次性准备（只做一次）

### 1.1 创建 Publisher

1. 打开 https://marketplace.visualstudio.com/manage
2. 用 Microsoft 账号登录 → **Create publisher**
3. 填表：

   | 字段 | 说明 |
   | --- | --- |
   | **Name** | 市场页上显示的名字，**以后可改** |
   | **ID** | ⚠️ **永久不可改**，必须与 `package.json` 的 `publisher` **完全一致**（大小写敏感） |
   | Verified domain | 可跳过；需要自有域名 + DNS TXT 记录 |
   | Description / Logo / website / Support / repo | 展示信息，可后补 |

   本仓库当前的值：

   ```jsonc
   { "publisher": "liivon" }
   ```

### 1.2 生成 PAT（Personal Access Token）

在 Azure DevOps 里生成（Marketplace 复用它的身份体系）：

1. https://dev.azure.com → 登录 → 创建一个组织（免费，名字随便）
2. 右上角 **User settings** → **Personal access tokens** → **New Token**
3. **关键设置**：

   | 项 | 必须选 |
   | --- | --- |
   | Organization | **All accessible organizations** ← 选成具体某个组织是 401 的头号原因 |
   | Scopes | **Marketplace → Manage** |

4. 有效期最长 1 年，记下到期日
5. **立刻复制 token**（只显示一次）

### 1.3 登录 vsce

```bash
npx --yes @vscode/vsce login liivon
# 粘贴 PAT（输入不回显）
```

> PAT 是凭证。**不要把它写进任何文件、不要贴到聊天/截图里。**
> 登录信息由 vsce 自己保存；过期后重新 `login` 即可。

> ⚠️ **PAT 的寿命是有限的**：官方文档声明 **2026-12-01 起 Azure DevOps 的全局 PAT 退役**，
> 之后要用 Microsoft Entra ID 身份认证（`vsce publish --azure-credential`）或 CI 里的 workload identity federation。
> 所以：**先用手动 PAT 把扩展发出去**，把认证迁移当成后续独立任务，别卡在发布上。

## 2. 日常发版流程

### 2.1 配置一次：让 CI 能自动发布

在 GitHub 仓库 → **Settings → Secrets and variables → Actions → New repository secret**：

| Secret | 用途 | 必需吗 |
| --- | --- | --- |
| `VSCE_PAT` | 发布到 **VS Code Marketplace**（Azure DevOps 的 PAT） | 想让官方市场自动化就必需 |
| `OVSX_PAT` | 发布到 **Open VSX**（覆盖 Cursor / VSCodium / Gitpod） | 可选，但**只需一个 GitHub 账号**，成本最低 |

两个都没配也不会失败，只是在 Actions 里各给一条 warning（只发 GitHub Release）。

**关于选择顺序的建议**：`VSCE_PAT` 需要先有一个 Azure DevOps 组织，
而创建新组织现在**要求绑定 Azure 订阅**（免费层即可，`Azure for Students` 用学校邮箱
验证、免信用卡）。如果你暂时不想折腾 Azure，就先配 `OVSX_PAT` ——
去 <https://open-vsx.org> 用 GitHub 登录 → Settings → Access Tokens 生成，两分钟搞定，
然后推 tag 就有自动发布了。

配好之后，推 tag 就会**自动构建四平台 + 自动创建 GitHub Release + 自动发布**。

#### 各步骤的自动化程度

| 步骤 | 未配 secret | 配了 secret |
| --- | --- | --- |
| 编译 4 平台引擎 | ✅ 自动 | ✅ 自动 |
| 打 4 个平台 vsix | ✅ 自动 | ✅ 自动 |
| 创建 GitHub Release | ✅ 自动 | ✅ 自动 |
| 发布到 Marketplace | ❌ 手动传 4 次 | ✅ 自动 |
| 发布到 Open VSX | ❌ 手动 | ✅ 自动 |

### 2.2 每次发版（复制这几行）

```bash
# 1) 改代码并自测
npm test                      # 引擎 29 + 端到端 8 + RPC 29 + Webview 32

# 2) 更新 CHANGELOG（会显示在 Marketplace 的 Changelog 标签页）
#    编辑 docs/CHANGELOG.md

# 3) 先把改动提交掉 —— npm version 要求工作区是干净的，有未提交改动会直接报错
git add -A
git commit -F <消息文件>       # ⚠️ 中文消息务必用 -F 读文件，
                              #    用 -m "中文" 会被 PowerShell 转成字面 ? 永久损坏

# 4) 升版本号（改 package.json + 自动 commit + 打 tag v0.1.1）
npm version patch             # 或 minor / major

# 5) 推代码 + 推 tag
git push && git push --tags
```

推完 tag 之后什么都不用做 —— CI 会：

| 步骤 | 说明 |
| --- | --- |
| ① 三个 runner 编译引擎 | win32-x64 / linux-x64 / darwin universal（x64+arm64） |
| ② 合成 4 个平台专用 vsix | 每个平台一个包，Marketplace 只发给对应平台 |
| ③ 自动创建 GitHub Release | 4 个 vsix 直接挂在 Release 上，用户可从那里下载 |
| ④ 自动发布到 Marketplace | 用户 VS Code 里会**自动提示更新** |

### 2.3 只想重新构建、不发版

仓库 → **Actions** → `Build VSIX` → **Run workflow**：

- 勾 **publish** → 构建完顺手发布到 Marketplace（必须已配 `VSCE_PAT`，否则报错）
- 不勾 → 只构建，产物在 run 页面底部的 **Artifacts → `vsix`**

也可以在 Actions 页面点 **Re-run all jobs** 重跑某个 tag 的构建（Release 上传是幂等的，不会报"已存在"）。

### 2.4 为什么必须用 `npm version`

Marketplace **不允许同一个版本号发布两次**，覆盖也不行。`npm version` 帮你做三件事：
改 `package.json` 的 version、commit、打 tag —— 三者一致才不会发错。

### 2.5 手动更新（没有 PAT 时的退路）

第一次是 `New extension`；**后续更新不能用 `New extension`**，要在已有扩展的管理页里：

```
https://marketplace.visualstudio.com/manage/publishers/liivon/extensions/depscan/manage
→ 右上角 Update → 拖入新的 vsix
```

多平台包要**逐个平台各传一次**。这件事很容易漏（只传了 Windows 就以为更新完了），
所以**强烈建议尽早配上 `VSCE_PAT` 走 CI 自动发布**。

## 2.6 用户侧怎么拿到更新

| 分发渠道 | 用户怎么装 | 会自动更新吗 |
| --- | --- | --- |
| VS Code Marketplace | 扩展面板搜 `DepScaner` 一键安装 | ✅ 会 |
| GitHub Release（vsix） | 下载 → 扩展面板 → `Install from VSIX` | ❌ 不会，要手动重装 |

这也是为什么 Marketplace 是主渠道：它解决了"用户怎么知道有新版本"的问题。

`npm run publish` 会做这些预检，任何一条不过就直接退出：

- 目标 vsix 文件是否存在（文件名随平台变化：通用包 `depscaner-0.1.0.vsix`，
  平台专用包 `depscaner-win32-x64-0.1.0.vsix`）
- 打印待发布包的**体积与生成时间**，并列出目录里其它 vsix ——
  避免手滑把上一次的旧产物传上去（实测踩过：旧包里是旧引擎）
- `engines/` 里是否有引擎；平台专用包是否覆盖了该平台
- `publisher` 与仓库归属是否对得上（对不上只提示，不拦）
- 只含单一平台引擎却要发通用包时，提示改用平台专用包

## 3. 平台专用包 vs 通用包

引擎是**原生二进制，不能交叉编译**。所以：

| 场景 | 命令 | 效果 |
| --- | --- | --- |
| 只支持 Windows | `npm run publish:win32-x64` | Marketplace 只把包发给 Windows 用户 |
| 只有本机引擎、想发通用包 | `npm run package` | ⚠️ 所有平台都能装到，但非 Windows 用户会看到「引擎缺失」 |
| 三平台都支持 | 在各平台各跑 `build:core` → 放进 `engines/` → `npm run package` | 用户侧零工具链依赖，代价是 vsix 体积 +6~12 MB |

补齐其它平台的正确做法有两条，**推荐走 CI**：

#### 路线一：GitHub Actions（推荐，零成本）

仓库是 **public** 的 → GitHub Actions 构建分钟数**免费且不限量**。

`.github/workflows/build-vsix.yml` 已经写好了整套流程：

```
① 四个原生 runner 各编译一次引擎 + 跑引擎自测 29 项
     windows-latest → win32-x64
     ubuntu-latest  → linux-x64
     macos-13       → darwin-x64   (Intel)
     macos-14       → darwin-arm64 (Apple Silicon)
② 汇到一个 ubuntu runner：npm ci → build:prod → 逐平台打 vsix
③ 打 tag（v*）时自动建 Release 并附上四个 vsix
   手动触发时可勾选 publish，直接把四个包发到 Marketplace（需 VSCE_PAT secret）
```

**怎么用**：仓库页面 → **Actions** → 左侧 `Build VSIX` → **Run workflow**。
下载生成的 `vsix` artifact，或直接在 Release 里拿。

两个实现细节值得记住：

- **artifact 不保留文件权限位** → 引擎二进制先打成 `tar.gz` 再上传，
  下载后解开，并 `chmod +x`。否则 Linux/macOS 上的引擎不可执行。
- **不打「通用包」** → 通用包会被 ARM Linux / Windows ARM 之类的平台也装到，
  然后报「引擎缺失」，比「搜不到」更糟。只发平台专用包。

#### 路线二：手动在各平台构建

```bash
# 在 Linux 机器上
npm ci && npm run build:core && npm run collect:engine
# → engines/linux-x64/depscaner-core
```

把整个 `engines/linux-x64/` 拷回主开发机（`engines/` 已在 `.gitignore` 里，
所以要用网盘/制品库传，不能靠 Git），再统一 `npm run package`。

> 注意：单个 vsix 里可以同时装多个平台的引擎，这样发出去是**通用包**。
> 除非你确认所有内置平台就是你支持的全部平台，否则优先用平台专用包。

## 4. 发到 Open VSX（可选，覆盖 Cursor / VSCodium / Gitpod）

Open VSX 归 Eclipse 基金会，**不需要 Azure 账号**：

```bash
# 1) https://open-vsx.org → 用 GitHub 登录 → Settings → Access Tokens 生成
# 2) 设置环境变量（PowerShell）
$env:OVSX_PAT = "你的token"
# 3) 发布
npm run publish:openvsx
```

也可以把 PAT 持久化进用户级环境变量（`setx OVSX_PAT "xxx"`），避免每次开新终端都要设。

## 5. 常见报错对照表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `401 Unauthorized` | PAT 过期 / Organization 没选 **All accessible organizations** / 权限不是 Marketplace-Manage | 重新生成 PAT |
| `403 Forbidden` | 同上，或账号没有该 publisher 的权限 | 确认登录账号与 publisher 所属账号一致 |
| `Extension 'x@1.0.0' already exists` | 版本号重复 | `npm version patch` 后重新打包 |
| `The publisher ID does not match` | `package.json` 的 `publisher` ≠ 创建的 ID | 改 `package.json`（首次发布前还来得及） |
| 用户报「引擎缺失」 | vsix 里没有对应平台引擎 | 改发平台专用包，或补齐 `engines/` |
| `ERROR Invalid extension manifest` | `package.json` 里引用了不存在的 `%nls key%` | 跑 `npm run check:webview`（已含 NLS 键位校验） |
| 上传很慢 / 超时 | vsix 太大 | 检查 `.vscodeignore`；本项目已排除 `src/ scripts/ samples/ engine/` |
| `npm run package` 报 `EBUSY` | 本地跑着 DepScaner，`engines/.../depscaner-core.exe` 被锁 | 禁用扩展或关掉那个 VS Code 窗口，再打包 |
| 发布后用户装了没反应 | 包里没有对应平台的引擎 | 用平台专用包；或补齐 `engines/` |

## 6. 发布后自检

1. 打开 Marketplace 页面，确认 **README 渲染正常**（相对图片链接是否还指向仓库）
2. 在**一台干净的机器/新用户档案**里搜到并安装，跑一次「三步开始」
3. 确认 `DepScaner: 为什么是近似？（精度诊断）` 能给出可执行的下一步
4. 管理页的「Statistics」看安装量；用户反馈走 `bugs.url`（`repository/issues`）

## 7. 版本号怎么定

遵循 [语义化版本](https://semver.org/lang/zh-CN/)：

- **patch**：修 bug、改文案、修精度判定
- **minor**：新增命令 / 新依赖类型 / 新配置项
- **major**：破坏兼容（配置项重命名、`engines.vscode` 大幅提升、引擎协议版本不兼容）

引擎协议版本在 `engine/include/depscan/protocol.hpp` 里，
如果它与旧版扩展不兼容，必须同时升 major 并保证扩展侧有版本检查 —— 否则用户升级后会看到难以理解的报错。

## 8. 图标：为什么是「代码画的」

图标有两个产物，要求完全不同，所以**不能用同一张位图糊弄**：

| 产物 | 用途 | 硬性要求 |
| --- | --- | --- |
| `media/icon.png` | 扩展图标（扩展页、Marketplace 列表） | **PNG**，文档建议 **128×128**，要能透明 |
| `media/activitybar.svg` | 活动栏容器 / 侧边栏视图图标 | **单色**（只准 `currentColor`），24×24 |

`npm run icon`（`scripts/make-icon.mjs`，纯 Node，连 PNG 编码都是自己写的，无图像库依赖）
一次生成两个产物，造型是那只**煎蛋**（不规则蛋白 + 蛋黄 + 高光）。

**为什么不直接塞一张画好的位图**

1. 位图做不了活动栏图标 —— VS Code 要求单色 `currentColor`，彩色位图在深色主题下要么是
   一块白方块，要么看不见。
2. 128px 的位图通常带不透明白底（.ico 尤其如此），贴到深色主题上就是「白底方图」。
3. 改一次造型就得重画一遍、还要导出两个尺寸两种格式；代码画只改 `BLOT` / `YOLK` 几个常数，
   而且**两个产物共用同一套几何**，不会出现「PNG 改了、SVG 忘了改」的漂移。

**守卫**：`scripts/check-webview.mjs` 第 10 节断言了这些平台约束 ——
PNG 魔数、IHDR 必须是 128×128、必须是 RGBA（圆角外要透明）；
SVG 必须 `viewBox="0 0 24 24"`、含 `currentColor`、**不写死颜色**；
`package.json` 的 `icon` 与活动栏容器/视图的 `icon` 都指向生成产物。
图标是二进制，改错了没有任何编译/类型检查会提醒你，所以只能靠自检。

**改造型**：只改 `scripts/make-icon.mjs` 里的常量和谐波系数，然后 `npm run icon`；
改完**必须重跑 `npm test`**（守卫会告诉你有没有踩到平台约束）。
拿到设计稿（比如 `.ico` / `.png`）时把它当**参考**，用代码重画 —— 不要直接提交位图。
