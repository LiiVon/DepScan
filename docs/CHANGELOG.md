## 0.1.1

### 改名（又改回来了）

- **产品名与扩展 ID 定回 `DepScan` / `liivon.depscan`** —— 也就是**已经上架过 0.1.0 的那条**。
  因此这一版是**对已有商品页的更新**：安装量、评分、评论都保留，老用户**自动收到更新**。
- 中途曾改名为 `DepScaner` / `liivon.depscaner`，但那条**从未发布**，所以没有用户受影响；
  只有本机/测试机装过的话，请卸载 `liivon.depscaner`（两个都装会出现两套侧边栏图标与两套命令）。
- 一起回到旧名的还有：命令 id 与配置键前缀（`depscan.*`）、侧边栏/输出通道/状态栏显示名、
  引擎可执行文件名（`depscan-core`）、索引缓存目录（`.vscode/depscan-cache`）。
  内部标识（C++ 命名空间与 `depscan/` 目录、CMake 目标）现在与产品名完全一致，不再错位。
- 教训写进了 [06-发布与版本管理 §0.1](06-发布与版本管理.md)：**上架后 ID 就是永久的，
  改 ID 等于换一条商品页**；显示名随时能改，所以「名字不好听」不该成为改 ID 的理由。

### 图标

- **扩展图标换成煎蛋，而且是代码画的**：`npm run icon` 一次生成两个产物 ——
  `media/icon.png`（128×128 PNG，圆角外透明）与 `media/activitybar.svg`
  （24×24 单色 `currentColor`，深色/浅色主题都看得见）。
  两个产物的平台要求本来就不同（PNG vs 单色 SVG），塞同一张位图必然顾此失彼；
  代码画还能让两个产物共用同一套几何，不会「PNG 改了、SVG 忘了改」。
  自检里加了守卫（PNG 必须是 128×128 RGBA、SVG 不许写死颜色），见 docs/06 §8。

### 新增

- **阅读路线（Reading Route）**：从程序入口（`main` / `WinMain` / `DllMain` …）出发，
  按调用关系生成一份**有序**的阅读清单。
  · 引擎侧 `route` RPC：广度优先 / 深度优先两种策略，函数级与文件级两个粒度，
    标注「同名候选」这类不可靠的步骤；遍历在引擎侧完成，只回传前 N 步与前沿统计。
  · 界面：侧边栏新增「阅读路线」视图（TreeView）—— 纵向缩进列表、点击跳源码、
    标题栏可切换策略 / 粒度 / 重新生成；⚠ 标记不可靠步骤，悬停看原因。
  · **候选与纠偏**：同名定义会被按名字消解，因此「项目里还有别的同名函数」就等于
    可能走错边。这类步骤标 ⚠，展开「候选」列出所有同名定义（含文件位置与当前用的那一个），
    点一个就改走它、点「当前」就撤回（引擎侧 `overrides` 参数）。
  · **从光标处开始读**：新增 `nodeAt` 接口（光标位置 → 所在函数），
    编辑器右键 / 侧边栏 / 标题栏都能换起点，库项目不再只能看着「找不到入口」。
  · **泳道图**：每个文件一条泳道、横轴是步号，橙色箭头 = 控制权交给了另一个文件。
    可缩放（矢量）、可导出**自包含单文件 SVG**、点圆点跳源码；
    **导航与依赖图面板一致**：拖拽平移、滚轮以鼠标位置为锚点缩放（滚轮一格 ≈1.17 倍、
    触控板小步连续平滑）、键盘 `+` `-` `0` `f`，平移带边界保护（不会把图拖飞）。
    布局与 SVG 生成都是纯函数，因此能离线断言（见下）。
  · 辅助脚本 `npm run route:dump`：把路线按树打到终端（含候选），
    `--svg` / `--html` 还能导出泳道图与整页离线预览 ——
    改了消解逻辑后可以直接 `git diff` 看顺序有没有变，不用开 VS Code。
  见 [07-阅读路线](07-阅读路线.md)。
- **降噪：折叠「纯转发 / 小函数」**：一行 getter 与纯转发函数不再占一个阅读步骤
  （函数体 ≤3 行**且**只调一处才算；`Engine::describe` 这类虽然只有 3 行、但调了两处的会保留）。
  插件默认开着，标题栏 `$(filter)` 可随时关掉；引擎侧 `skipTrivial` 默认关，RPC 层保持原样。
  **折叠不是静默删除**：被折叠的名字挂到最近的那个保留步骤上，视图顶部报「已折叠 N 个」，
  那一步的 tooltip 里列出名字（同时带上函数体行数）。
  `npm run route:dump -- --trim` 也能在终端看到同样的效果。
- **层视图（层摘要 + 分页）**：层 = 从起点算的跳数 + 1（所以第 1 层就是起点本身）。
  大项目下第 3 层就可能扇出上百个函数，一次铺开只是又一面墙 ——
  现在一页能看完的层默认展开、**会被分页的层默认收起**（先只看一行摘要：
  「第 3 层 · 87 个步骤 / 21 个文件」）；一层超过 15 个就先给一页，末尾一行
  「还有 N 个未列出 —— 点这里继续展开」。分页只是换个摆法，**不重新问引擎**。
  标题栏 `$(layers)` 开关；`npm run route:dump -- --layers` 能在终端看到同一份清单
  （用的是界面同一个纯函数，免得文档与 UI 漂移）。
- **库项目也能起头（导出接口候选）**：没有 `main` 时不再只丢一句「找不到入口」，
  而是把**起点候选**列出来：程序入口 → 公开接口（声明在 `include/` 这类目录下、且自己有下游）→
  其余公开接口 → 调用图上的「根」（没人调用、但会调别人）。
  每行都给出判据（是不是公开面、多少调用者/下游、公开声明在哪个头文件），
  **引擎不替你挑** —— 起点错了后面整条顺序都是错的，所以由读代码的人点一个。
  新增 `entries` 接口与 `npm run route:dump -- --entries` 出口；
  另加 `samples/libdemo`（5 个文件的库，故意没有 main）作为这个场景的样例。
- **公开面标注（V4）**：把「声明在 `include/` 这类目录下」标出来 ——
  依赖图的树/表格行多一个 `公开` 角标、详情里列出公开声明在哪个头文件、图例在这条角标存在时才加，
  阅读路线里公开接口那一步换成接口图标（悬停看声明位置）。
  **画布上刻意不画**：大项目里公开面往往是大多数，满屏画环会把真正的关系滤掉。
  判定是**目录约定**（`include/` `inc/` `public/` `api/`），为什么只能是约定见 docs/04 §2.6。
- **架构边界检查（V4）**：两条**可证明**的检查报到「问题」面板（点一下跳到那一行）：
  · 公开头文件引用了内部实现（`depscan.public-api-leak`）—— 装了库的人编译不过
  · 目录之间互相 include 成环（`depscan.directory-cycle`，Tarjan 强连通分量，三目录成环也算）
  刻意**不**按目录名猜层次（那是约定不是事实，误报会让人直接关掉检查）；
  同目录内部互引不算；只认解析到项目内文件的边（漏报安全，误报致命）。
  开关 `depscan.checks.enabled`，命令「架构边界检查」，CI 出口 `depscan-core --once --violations`
  （有违规退出码 1）。见 [08-架构边界检查](08-架构边界检查.md)。

### 修复

- **真实项目上在「1/5 发现文件」就失败**：`No mapping for the Unicode character exists in the
  target multi-byte code page`（用户在公司大项目上实测发现；自造的 ASCII 样例永远踩不到）。
  引擎内部路径都是 UTF-8，而 MSVC 的 `std::filesystem::path` / `std::ifstream` 在窄字符串与
  宽字符互转时用的是**进程 ANSI 代码页**（中文机器 = 936/GBK）——项目里只要有一个文件名
  不是合法 GBK 字节序列（emoji、日文、韩文、部分中文组合），轻则文件静默读不到、
  重则直接抛上面这句。两处一起修：① exe 链接 `activeCodePage=UTF-8` 清单；
  ② 所有路径转换改走显式 `CP_UTF8` 的 `util::toFsPath` / `util::fromFsPath`。
  新增回归测试 `npm run test:unicode`（带空格的根目录 + `中文目录/` + `emoji-😀/`，已接进 `npm test`）。
- **界面语言是中文、侧边栏视图标题却是英文**：清单里的 `%view.x%` 只跟随 VS Code 显示语言，
  而「界面语言」设置管不到它 —— 两个语言不一致时就是半截翻译。
  现在四个视图标题改从运行期文案取（`TreeView.title` 能在运行期改），跟着设置走。
  （命令面板里的命令标题仍只跟显示语言，那是平台行为。）
- **阅读路线看不出当前策略**：策略 / 粒度 / 降噪 / 层视图都是无状态图标按钮，点完只看到列表变了，
  看不出现在是广度优先还是深度优先、函数级还是文件级。
  现在视图标题右边会写出来：`广度优先 · 函数级 · 已降噪 · 层视图`。
- **符号位置停在声明 / 调用点，而不是定义处**：合并符号时先改了 `declaration` 再判断
  要不要搬位置，条件恒为假 —— 于是「定义比声明（甚至比调用点）晚出现」的函数
  （例如 `demo::setVerbose`，定义在 `src/util/logger.cpp:14`，但在 `src/main.cpp:9` 就先被调用了）
  位置永远停在第一处。影响面是「点一步跳到的不是函数体」，对读代码这件事直接有害。
  现在连 `module` 一起跟着定义走，并补了断言。

### 修正

- 「可能是错边」的判定改了：原定义是「同一个父节点下有 ≥2 个同名子节点」，
  但真实出错场景恰好相反 —— 图里别处还有个同名函数、消解挑错了那一个，
  此时父节点下**只有一个**同名子节点，旧定义什么都不会报。
  改为「项目里还有别的同名定义」后，候选集也顺手拿到了（demo 上 `describe` 命中）。

### 修复

- **成员函数调用几乎无法解析**（影响面最大的一处）：`obj.method()` / `ptr->method()`
  会被误登记成**函数声明**。原因有两条：
  1. `return app.start(args);` 里 `return` 和 `app` 都是 identifier，
     被「语句起点到名字之间有 identifier 就算有返回类型」这条启发式当成了声明；
  2. 词法器没有把 `->` 合成单个 token，于是「名字前一个 token 是不是成员访问符」判断失手。
  后果不只是多几个假节点 —— 假节点是无限定名，会**污染按名字索引的符号表**，
  让真正的 `demo::Application::start` 再也匹配不上。修复后 `samples/demo` 的
  节点数 69 → 60（去掉 9 个假节点），调用边去掉了 3 条假边。
- 引擎崩溃：**子线程里逸出的异常会让整个进程猝死**（Windows 退出码 `0xC0000409`）。
  扫描被包在三层线程里（RPC 线程 → scanner.run → 解析线程），任何一层漏掉 try/catch
  都会变成「无法建立索引」。现在三层都有兜底，单个文件解析失败只会被跳过并记入警告。
- 编译数据库变化后不再复用旧缓存（旧缓存会让精度一直停在「近似」）。
- 精度从两级（精确 / 近似）改为三级（精确 / 部分精确 / 近似）。

### 新增（诊断能力）

- 命令 `DepScan: 为什么是近似？` —— 逐项报告编译数据库查找结果与下一步该做什么。

## 0.1.0 — 首个可用版本

### 新增

**分析引擎（C++20 / CMake，独立进程，零外部依赖）**

- 五类依赖识别：`includes` / `calls` / `inherits`+`uses` / `refs` / `links`
- 内置 C/C++ 词法与结构解析器：注释与字符串剥离、原始字符串、跨行续行、`operator` 重载、命名空间与类作用域限定
- `#include` 宏展开（`#define X "a.h"` → `#include X`）与三级精度标注（精确 / 部分精确 / 近似）
- `compile_commands.json` 自动发现与解析：提取 `-I/-isystem/-D`，逐文件还原真实编译参数
- 符号表构建与引用消解（同名候选优先同文件，>3 候选聚合为未解析节点）
- CMake 构建模型解析：`add_executable` / `add_library` / `target_link_libraries` → 目标与链接依赖
- 多线程并行解析（任务队列 + 原子分配），文件级结果复用
- 服务端 k 层 BFS 子图裁剪，服务端按目录聚合的全局架构视图
- 磁盘缓存（文件级 `mtime + size` + 全量**配置指纹**：根目录 / 编译数据库路径与 mtime / include 路径 / 宏），编译数据库变化即整份作废
- 导出：JSON / DOT / Mermaid
- 单文件增量更新与「受影响文件」查询

**VS Code 插件（TypeScript）**

- 命令：重建索引 / 取消索引 / 清理缓存 / 查看索引状态 / **为什么是近似？（精度诊断）** / 查看依赖图 / 查看当前符号的依赖图 / 导出 / 生成指引 / 打开文档 / 刷新依赖视图
- 侧边栏：**操作视图**（常用命令一次点击，含语言子菜单与当前精度）、索引状态视图（进度、统计、三级精度、警告）、依赖视图（双向依赖树，逐层展开）
- 状态栏：实时索引进度、规模与当前精度
- 编辑器与资源管理器右键菜单
- 保存事件触发的增量重建（400ms 防抖）+ 文件增删监听
- **监听 `compile_commands.json` 的增删改**，防抖 800ms 后自动全量重新索引（先索引、后生成编译数据库也能自愈）
- 中英双语 UI（默认中文，可 `auto` 跟随 VS Code；侧边栏与依赖图工具栏均可切换）
- 完整配置项（见 `docs/05-性能与配置参考.md`）
- 引擎定位：配置 → 内置 `engines/<platform>-<arch>/` → 开发态构建目录

**Webview 可视化（无第三方前端依赖）**

- Canvas 力导向图：拖动节点、滚轮缩放、平移、单击跳转源码、双击展开下一层
- 三视图联动：依赖图 / 层级树 / 表格（选中同步高亮与导航）
- 方向开关（双向 / 上游 / 下游）、层级 k 调节、按目录聚类、外部符号显示开关
- LOD：节点数 > 260 改用网格布局，> 400 自动按目录聚类；标签随缩放等级显隐
- 导出 PNG（离屏 2 倍渲染整图）/ SVG（矢量）/ JSON / DOT / Mermaid
- 节点与边按类型着色，实线 = 精确、虚线 = 近似

**工程与质量**

- `samples/demo`：15 文件示例项目，含循环包含与分层违规
- 引擎自测 29 项（词法 / 预处理 / 五类依赖 / 图 / 缓存格式 / glob）
- JSON-RPC 协议冒烟测试 24 项（真实子进程驱动全部方法，含 compile_commands 精确路径）
- Webview 离线自检：脚本语法 + DOM id 对齐 + 内嵌 JSON 解析 + CSP 校验
- 压力测试脚本：10 万行与百万行两档合成工程，输出可复现报告
- 三平台引擎分发方案与打包脚本

### 已知限制

- 无 `compile_commands.json` 时，调用 / 继承 / 类型依赖为结构级近似，重载决议与模板实例化不保证正确
- 链接依赖目前只解析 CMake；Makefile / Bazel / qmake 需借助 `compile_commands.json`
- libclang 精确语义分析路径已预留（`-DDEPS_USE_LIBCLANG=ON`），本版本默认关闭
- 峰值内存未插桩
- 磁盘缓存为文本格式，超大型项目缓存文件可能较大

- `.depscan.json` 自定义分层规则
- 符号级重载区分与模板实例化展开
- 差异视图（对比两个版本的依赖变化）
