# 07 · 阅读路线（Reading Route）

> 打开一个大项目，真正的问题不是「有哪些依赖」，而是**从哪读起、按什么顺序读**。
> 这一篇讲 DepScaner 怎么回答这个问题。

---

## 1. 它和另外三张图的区别

| | 回答的问题 | 数据形态 | 渲染方式 |
| --- | --- | --- | --- |
| 文件依赖图 | 这个文件和谁有关？ | 无序子图 | 力导向图 |
| 符号子图 | 这个函数和谁有关？ | 无序子图 | 力导向图 |
| 全局架构图 | 项目分成几块？ | 按目录聚合 | 力导向图 |
| **阅读路线** | **先读什么、再读什么？** | **有序序列** | **有轴的列表 / 泳道** |

关键差别在最后一行：**前三个的核心信息是「关系」，路线的核心信息是「顺序」**。

力导向图的本质是无序的 —— 它为了减少连线交叉会把节点到处甩。用力导向图渲染「阅读顺序」，
等于把最重要的信息抹掉。所以阅读路线**不能**做成第四张力导向图，它需要一根轴。

---

## 2. 起点：main

路线的默认起点是程序入口，按顺序尝试：

```
main → wmain → WinMain → wWinMain → DllMain → mainCRTStartup → wmainCRTStartup
```

优先取**项目内有真实定义**的那个（跳过头文件里的声明和项目外的符号）。

> 库项目没有 `main` 怎么办？**从光标处开始读**（编辑器右键 / 侧边栏「操作」/ 标题栏
> `$(target)`）：引擎把 `(文件, 行号)` 换算成「该处所属的函数」，再拿它当起点。
> 界面上的「起点回到 main」可以随时撤销（只在真改过时出现）。
> 底层是两个接口：`nodeAt`（光标 → 节点）与 `route` 的 `from`（任意节点 id 都能当起点）。

### 2.1 没有 main 的库项目：导出接口候选

库根本没有 `main`，但「从哪读起」这个问题照样存在 —— 答案是它的**公开接口**。
引擎不自己挑一个（理由见下），而是把候选连同判据一起给出来，界面上点一个就从那里开始读。
样例是仓库自带的 `samples/libdemo`（5 个文件，故意没有 main）：

```
起点候选（共 3 个，有 main：否）：
  [公开接口] mean	src/math.cpp:16	调用者 0 / 下游 1	公开声明 include/libdemo/math.h:10
  [公开接口] join	src/text.cpp:9	调用者 0 / 下游 1	公开声明 include/libdemo/text.h:9
  [公开接口] add	src/math.cpp:11	调用者 1 / 下游 1	公开声明 include/libdemo/math.h:7
```

排序规则（`findEntryCandidates`，每条都有断言钉着）：

| 级别 | 判据 | 为什么 |
| --- | --- | --- |
| 0 | `main` / `WinMain` / `DllMain` … | 有程序入口就先读它，这条最确定 |
| 1 | 公开接口 **且**自己有下游 | 你要读的 API，读下去还有东西 |
| 2 | 其余公开接口 | 能读，但读下去是叶子（读完了就没了） |
| 3 | 项目里没人调用、但它会调别人（调用图上的「根」） | 没有 `include/` 的项目只能靠它起头 |

两个刻意的决定：

1. **「公开面」按目录约定判**：`include/`、`inc/`、`public/`、`api/` 下的文件算公开接口
   （也就是安装规则最常见的写法 `install(DIRECTORY include/ ...)`）。
   没有编译数据库时，「导出符号」在语法层是看不见的 —— 既没法看 `__declspec(dllexport)`，
   也不知道 CMake 里的 `PUBLIC`/`PRIVATE`，只能靠这个约定。它不完美，但**可核对**：
   界面上会把「公开声明在哪个头文件」一并显示出来。
2. **引擎不替你挑起点**。路线的全部价值就是**顺序**，而顺序由起点决定 ——
   替你猜一个看似聪明，实际是把「猜错你也不知道」塞给用户。
   所以库里 `route(from: '')` 会直接失败（错误信息指向 `entries`），由界面把候选列出来让你点。

命令行出口：

```bash
npm run route:dump -- --root samples/libdemo --entries                        # 起点候选
npm run route:dump -- --root samples/libdemo --from func:libdemo::mean        # 从候选起头
```

> `entries` 对**有 main 的项目**也有用：demo 上它会给出 6 个（`main`、
> `config`（公开接口）、`logLine` / `Engine` / `reset` / `itemCount`（调用图上的根））。
> 平时用不到，但它是「这个项目的入口在哪」的一个可打印答案。

路线里每一步都会带上**公开面**（`apiHeader` / `apiLine`）：声明落在 `include/` 这类目录下的
步骤会换成接口图标，悬停显示「公开接口：include/...:行号」。
这是读库时最需要区分的一件事 —— 哪些是 API（别人会用），哪些是实现（内部细节）。
判定规则与它为什么只能是目录约定见 [04-解析与精度](04-解析与精度说明.md) §2.6。

## 3. 两个策略

调用图不是线性的：`main` 调 A、B、C，A 又调 D。所以「顺序」需要**一个遍历策略**来定义。

| 策略 | 走向 | 适合 |
| --- | --- | --- |
| **`bfs`（默认）** | 先读完 main 直接调用的，再进下一层 | **第一次读一个大项目** —— 先看骨架，再钻细节 |
| **`dfs`** | 跟着一条调用链一直走到深处，再回溯 | **追一条具体流程** —— 「这个请求到底经过了哪些函数」 |

**子节点的顺序按调用点的行号排**，所以阅读顺序跟随源码本身的书写顺序，而不是随机的图遍历顺序。
行号相同时按名字排 —— 这保证了**同样参数下路线完全可复现**，测试才能打靶断言。

## 4. 粒度与看法

同一份路线，三种摆法（前两个改**引擎参数**，第三个只是**界面看法**，不重新问引擎）：

| 摆法 | 参数 | 效果 |
| --- | --- | --- |
| **函数级** | `groupByFile: false`（默认） | 每一步是一个函数 |
| **文件级** | `groupByFile: true` | 每个文件只保留**首次进入**的那一步 |
| **按层**（标题栏 `$(layers)`） | 无（纯前端分组） | 先给「第 N 层」摘要，一层太大就分页（见 §4.1） |

文件级模式下，被折叠掉的中间步骤不会让父节点悬空 —— 每个保留下来的步骤会被接到
**最近的、还被保留的祖先**上，所以缩进结构始终完整。

所以在 demo 上：函数级 13 步、文件级 9 步；开着降噪时分别是 11 步与 8 步。

### 4.1 层视图：先给摘要，再逐层展开（V3）

调用树回答「谁调了谁」，层视图回答「**第几跳、这一跳有多少东西**」。
需要它是因为一个真实项目里第 3 层就可能扇出上百个函数 —— 把几百行一次铺开只是**另一面墙**。

层号 = 从起点算的跳数 + 1，所以第 1 层永远是起点本身。demo 上（降噪默认开着）的真实现样
（`npm run route:dump -- --trim --layers`，与界面同一个纯函数打印）：

```
第 1 层 · 1 个步骤 / 1 个文件
   1 main          src/main.cpp:6
第 2 层 · 1 个步骤 / 1 个文件
   2 start         src/app/application.cpp:9
第 3 层 · 3 个步骤 / 3 个文件
   3 config        include/demo/config.h:24
   4 run           src/core/engine.cpp:27
   5 render        src/ui/panel.cpp:13
第 4 层 · 4 个步骤 / 4 个文件
   6 trim          src/util/string_utils.cpp:7
   7 add           src/core/registry.cpp:8
   8 describe      src/core/engine.cpp:23
   9 describe ⚠    src/core/base.h:25
第 5 层 · 2 个步骤 / 1 个文件
  10 join          src/util/string_utils.cpp:30
  11 split         src/util/string_utils.cpp:15
✓ 路线已完整生成
```

demo 太小，5 层都在一页之内，所以这里看起来与调用树差不多。真正不同的是大项目：

```
第 1 层 · 1 个步骤 / 1 个文件          ← 起点，一页就够 → 默认展开
第 2 层 · 4 个步骤 / 3 个文件          ← 默认展开
第 3 层 · 87 个步骤 / 21 个文件        ← 超过一页 → 默认收起，先只看这一行摘要
第 4 层 · 300 个步骤 / 64 个文件
```

两条规则：

1. **只有会被分页的层才默认收起**。一页能看完的层收起来只是白多点一下；
   而大层默认铺开，就是又一面墙。
2. **一层超过一页（15 个）就先给一页**，末尾一行「还有 N 个未列出 —— 点这里继续展开」。
   分页只是换个摆法，**不重新问引擎**（`maxSteps` 一改就要重遍历，而这里要的是
   「同一份路线先少看一点」）。

层视图里步骤**只能展开候选**：它的子步骤已经在下一层里了，再嵌一次就是重复。
代价是失去了缩进，所以每一步的 tooltip 会多一行「由 #3 Application::start 调起」——
在层视图里，这一行就是「它从哪来」。

> 三者互不冲突：**降噪**决定「哪些算一步」，**粒度**决定「哪些步保留」，**层视图**决定「怎么摆」。
> 叠起来就是「每个文件首次进入 × 不琐碎 × 按层摘要」。

## 5. 参数

```jsonc
{
  "from": "",             // 起点节点 id；留空 = 自动找 main
  "strategy": "bfs",      // bfs（默认）| dfs
  "maxSteps": 200,        // 步数上限
  "maxDepth": 6,          // 跳数上限
  "projectOnly": true,    // 不进入项目外 / 未解析符号
  "groupByFile": false,   // 每个文件只保留首次进入
  "kinds": ["calls"],     // 参与遍历的边类型
  "skipTrivial": false,   // 降噪：折叠「纯转发 / 小函数」
  "trivialBodyLines": 3,  // 判「小函数」的函数体行数上限
  "overrides": {}         // 人工纠偏：{"<父节点 id>|<简单名>": "<改用的节点 id>"}
}
```

`overrides` 的 key 用**节点 id**而不是步号，是因为**步号会随纠偏本身变化** ——
在 `#5` 下换了一个候选，后面所有步号都可能移位，用步号做 key 的纠偏会在第二次应用时指错地方。
节点 id 在任何一次运行里都是同一个。

分隔符 `|` 是引擎与插件的硬约定（`engine/src/route.cpp` 的 `applyOverrides` 与
`src/views/routeTreeModel.ts` 的 `overrideKey`），两边都各有一条断言钉着。

**`projectOnly` 默认开着是有原因的**：真实项目里从 `main` 往下走一层就会撞上
`printf`、`std::vector::push_back`、平台 API。不挡掉的话，第 3 步开始就全是无关节点。
关掉之后这些外部符号会以 `<外部>` 聚合节点出现。

**`skipTrivial` 默认关**：RPC 层原样给出引擎算出的全部步骤，「要不要折叠」是界面上的选择
（插件默认**开着**，因为阅读清单里夹满一行 getter 时人是真的会漏掉真正要读的那几步）。
规则与「折叠不是静默删除」的做法见 §10。

另一个接口：

```jsonc
// nodeAt：光标位置 → 该处所属的函数（「从光标处开始读」用的就是它）
{ "method": "nodeAt", "params": { "file": "src/core/engine.cpp", "line": 29 } }
// → { "id": "func:demo::Engine::run", "name": "run", "file": "src/core/engine.cpp", "line": 27, ... }
```

它取的是**同文件中行号 ≤ 光标行的最后一个函数定义**，而不是「最近的任意符号」——
读代码时的直觉是「我在这个函数里」。光标上方没有函数时才退回其他符号，最后退回文件节点。

还有一个接口：

```jsonc
// entries：起点候选（main 优先；库项目看它的公开接口与调用图上的「根」）
{ "method": "entries", "params": { "limit": 50 } }
// → { "candidates": [
//     { "id": "func:libdemo::mean", "name": "mean", "file": "src/math.cpp", "line": 16,
//       "mainLike": false, "publicApi": true,
//       "apiHeader": "include/libdemo/math.h", "apiLine": 10,
//       "callers": 0, "callees": 1 } ],
//     "total": 3, "hasMain": false }
```

`limit <= 0` = 不截断；`total` 是未截断的真实数量（与 `limit` 无关，和候选列表一个路子）。
排序规则见 §2.1。

## 6. 返回结构

```jsonc
{
  "from": "func:main",
  "steps": [
    { "order": 1, "parent": 0, "depth": 0, "newFile": true,  "ambiguous": false,
      "candidateTotal": 0, "bodyLines": 6,
      "id": "func:main", "name": "main", "file": "src/main.cpp", "line": 6,
      "kind": "function", "precision": "approximate", "external": false },
    // 公开接口会多这两项（这里是 demo 里的 config：声明就在 include/demo/config.h 里）
    { "order": 3, "name": "config", "file": "include/demo/config.h", "line": 24,
      "apiHeader": "include/demo/config.h", "apiLine": 24 }
  ],
  "truncated": false,      // 是否因为 maxSteps / maxDepth 被截断
  "frontierNodes": 0,      // 还没展开的节点数
  "frontierFiles": 0,      // 还没展开的节点涉及多少个文件
  "maxReachedDepth": 3,
  "skippedCount": 0        // 被降噪折叠掉的琐碎步骤数
}
```
- `order` 就是**阅读顺序**（1-based）
- `parent` 指向父步骤的 `order`，0 表示起点 —— UI 用它做缩进和连线
- `newFile` 是「首次进入该文件」标记
- `candidateTotal` 是**别的同名定义的数量**（不含自己）；> 0 时还会多一个 `candidates` 数组，
  每项带 `id / name / file / line / declaration`，最多列 20 个（`candidateTotal` 仍是真实总数）：

```jsonc
{ "order": 10, "name": "describe", "ambiguous": true, "candidateTotal": 1,
  "candidates": [ { "id": "func:demo::Engine::describe", "name": "describe",
                     "file": "src/core/engine.cpp", "line": 23, "declaration": false } ] }
```

> 候选**不含自己**：前端把「当前用的那一个」自己拼出来放到列表最上面（带勾），
> 点它就是撤回纠偏。否则用户会遇到「选错了却回不去」。

- 折叠（`groupByFile`）时候选信息跟着保留 —— 折叠只改结构，不改「这一步可能是错的」这个事实。
- `bodyLines` 是**函数体行数**（含花括号那两行）；0 = 只有声明，或根本不是函数。
  降噪判「小函数」用的就是它 —— 用「定义行号 − 签名行号」会在多行签名上虚高，把真函数误判成小的。
- `skipped` 是**被降噪折叠掉的琐碎步骤名**（见 §10）；折叠掉的名字挂在**最近的那个保留步骤**上，
  `skippedCount` 是本次折叠的总数。两项同时为「空 / 0」时表示没有折叠。
- `apiHeader` / `apiLine` 是**公开面**（见 §2.1）：声明落在 `include/` 这类目录里时才有这两项；
  它是「别人能不能 include 到这个符号」的唯一依据，界面上据此换成接口图标。

## 7. 诚实标注：路线不是「精确调用栈」

无 `compile_commands.json` 时，**调用边是按名字消解的**。普通依赖图错一条边只是多一条线，
但**顺序图错一条边，后面整条路径都是错的** —— 所以这里的可信度必须显式暴露。

`ambiguous: true` 的判定：**这个名字在项目里还有别的定义**（`candidateTotal > 0`）。

> 一开始我把它定义成「同一个父节点下有 ≥2 个同名子节点」。那是错的：
> 同一个函数下连着调两个同名函数在真实代码里几乎不会发生，而**按名字消解真正会出错的场景
> 恰恰相反** —— 图里别处还有个同名函数，消解挑错了那一个，于是**父节点下只有一个同名子节点**，
> 旧定义什么都不会报。把判定改成「全局同名定义」后，候选集也顺手拿到了：
> 可以直接列出来让用户自己选（demo 上 `describe` 命中了这个情况）。

判定只收**定义**、不收声明：`class Engine { void run(); };` 的声明不是「读代码要去的另一处」，
收进来会让每个成员函数都变成「有候选」，把信号淹掉。

### 7.1 纠偏：让用户改，而不是替用户猜

候选不只是显示，还能**直接改**：

```jsonc
// 让「Engine::run 里那句 describe()」改走 Base::describe
{ "method": "route", "params": { "from": "",
  "overrides": { "func:demo::Engine::run|describe": "func:demo::Base::describe" } } }
```

三条实现约定（都有断言钉着，见 §8）：

1. **key 用 `<父节点 id>|<简单名>`，不用步号**（理由见 §5）；
2. 选中的节点**即使原本不是该父节点的子节点也照走** —— 图里解析到了别的同名函数，
   这正是纠偏要修的东西；行号沿用原调用点，所以排序与遍历策略的行为完全不变；
3. 传空 `overrides` 与不传的结果**逐字节一致** —— 纠偏必须可撤销。

> 这是「近似精度」在这条功能上最直接的代价，写在这里而不是藏在实现里。

## 8. 验收标准（打靶测试）

不给「好不好看」下断言，只给「顺序对不对」下断言。`scripts/test-rpc.mjs` 里的实测：

```
自动识别程序入口：func:main
路线生成 13 步
第 1 步是起点且没有父节点（main）
打靶：main → Application::start(#3) → Engine::run(#5) → Registry::add(#8)
projectOnly 生效：路线里不含项目外符号
每一步都带符号名与文件位置（可点击跳转）
每一步都带函数体行数（0 = 只有声明 / 不是函数）
有定义的函数定位到定义处：setVerbose → src/util/logger.cpp:14
按文件折叠：13 步 → 9 步
折叠后每一步都是「首次进入某文件」
折叠后仍然只有一个根
maxSteps 截断生效：3 步，未展开 3 个节点 / 3 个文件
同样参数下路线完全确定（可复现，测试才能打靶）
```

V2 新增的断言：

```
同名定义候选：describe 另有 1 处定义
ambiguous 与候选列表一致（不会出现「标了黄却无候选可选」）
候选里不含它自己 / 候选都带 id / 同名 / 文件位置
candidateTotal(1) ≥ 列出的候选数(1)，且列出的不超过 20
纠偏生效：run 下的 describe 改走 src/core/engine.cpp:23（同名兄弟由 2 个收敛为 1 个）
纠偏后 src/core/base.h:25 不再是 run 的子节点（原边被换掉）
空 overrides 与不传 overrides 结果一致（纠偏可撤销）
光标定位：src/main.cpp:7 → main
光标定位：src/core/engine.cpp:29 → run（取所在函数，不是最近的任意符号）
从光标处出发：起点是 run 而不是 main
```

V3 / V4 新增的断言（库项目起头 + 公开面）：

```
库项目没有 main：entries 如实说 hasMain=false
库项目的候选都是公开接口（mean / join / add），且都带 apiHeader

同样输入下候选顺序完全确定

从候选起头：mean → 共 3 步

路线步骤带公开面：config → include/demo/config.h:24
run 声明在 src/core/engine.h，不该被标成公开接口

内部实现（匿名命名空间）不会被标成公开接口
```

### 8.1 界面结构也能断言（`scripts/test-route-tree.mjs`）

### 8.3 泳道图也能量化断言（`scripts/test-swimlane.mjs`）

「画出来的东西」一向只能靠肉眼看，但只要把布局做成纯函数，大部分风险就能提前钉住：

```
泳道按首次进入的顺序排（先碰到的文件在上面）
每一步都落在自己文件的那条泳道里
任意两列都不重叠（名字再长也压不到邻居）
名字越长列越宽（列宽由这一步自己的名字决定）
箭头一律向右 —— 阅读顺序就是横轴方向
同泳道画直线、跨泳道画 S 形曲线
engine.cpp → panel.cpp 被标成跨文件
超过绘图上限时如实报数：画 N 步、未画 M 步
被截断掉的步骤不会留下悬空的边
文件名里的 & < > 被转义，带特殊字符时 SVG 依然良构
每个 CSS 变量都带兜底色 —— 导出成单文件也不会变成透明/黑色
页面脚本里没有画布绘制代码（绘制全在插件侧）
```

其中两条是踩出来的：

- **列不重叠要带浮点容差**：两列紧邻时理论间距恰好等于两半宽之和，
  但 `x` 是累加出来的，浮点会让它差个 `1e-13` —— 拿严格相等去比会**误报重叠**。
- **"良构"要自己校**：没有 XML 依赖，所以脚本里自带一个标签栈 + 文本段转义检查
  （这正是「数据里的 `&` 把 SVG 撑坏」对应的那个风险）。

> `--html` 更进一步：拿**真实页面**去浏览器里跑，并用 `postMessage` 投递数据，
> 完整走一遍面板的链路。这是除按 F5 之外唯一能验证 Webview 的手段。

## 9. 泳道图：把「换文件」画出来

侧边栏「阅读路线」是**调用树**，它回答「谁调了谁」；但读一个大项目时另一个问题同样重要：
**控制权在第几步从哪个文件交给了哪个文件？** 这件事用文字列表很难看清，所以这里回到画布。

在 `samples/demo` 上，13 步落在 9 条泳道里（顺序 = 首次进入的顺序）：

| 泳道（文件） | 这条泳道上的步 |
| --- | --- |
| `src/main.cpp` | #1 main |
| `src/util/logger.cpp` | #2 setVerbose |
| `src/app/application.cpp` | #3 Application::start |
| `include/demo/config.h` | #4 config |
| `src/core/engine.cpp` | #5 Engine::run、#9 Engine::describe |
| `src/ui/panel.cpp` | #6 Panel::render |
| `src/util/string_utils.cpp` | #7 trim、#12 join、#13 split |
| `src/core/registry.cpp` | #8 Registry::add、#11 Registry::size |
| `src/core/base.h` | #10 Base::describe ⚠ |

图上就是这个表：横轴一步一列，每条泳道一行，圆点落在对应列上。
这个 demo 里 12 条边中有 **11 条是跨文件**（它本来就是个「很多小文件」的示例，
连 `main` 调的那个一行 getter 都在另一个文件里），所以橙色箭头满屏 ——
这个数字会直接写在面板的状态行里，不用自己数。

> 上面是**未降噪**的 13 步 / 9 条泳道。插件默认开着降噪（§10），那时这张图是
> **11 步 / 8 条泳道 / 9 次换文件**：`logger.cpp` 整条泳道都消失了 ——
> 一个文件里只剩一行 getter 时，它本来也不值得单占一条泳道。

- **横轴 = 步号**（阅读顺序），**纵轴 = 文件**（每条泳道一个文件）
- 泳道顺序是**首次进入**的顺序 —— 先碰到的文件在上面，流向自然从上往下
- **橙色箭头 = 跨文件**（控制权换了文件），灰色箭头 = 同一个文件内部的调用
- **黄色圆点 = 这一步有同名定义**（可能走错边），与列表里的 ⚠ 是同一件事
- 因为横轴就是步号，**箭头永远只向右**，没有回头箭头
- 「向上指」的箭头 = 回到了之前读过的文件（真实项目里常见的回访动作）：
  比如 `string_utils.cpp` 里的 #7 与 #13 是自下而上的两条不同路径汇进的

### 9.1 布局是纯函数，所以能断言

`src/views/swimlane.ts` 不依赖 vscode、也不依赖 DOM，只把 `RouteResult` 算成坐标 + 一段 SVG 字符串。
因此「列会不会重叠」「箭头有没有往左跑」「文件名里的 `&` 会不会把结构撑坏」都能离线钉住（见 §8.3）。

两个具体取舍：

1. **一步一列，列宽由这一步自己的名字长度决定**：每个步号只对应一步，所以列宽不会与别的步骤打架，
   名字不必旋转、也不必省略到看不懂（超长会截成 `…`，完整名字在悬停提示里）。
2. **绘制留在插件侧，页面脚本只做导航 / 导出 / 点击**：Webview 里每多一行画布代码，
   就多一个「编译通过、类型正确，但打开页面一片空白」的机会 —— 这类问题只能在人肉打开页面时才发现。
   现在页面上显示的图与「导出 SVG」写出的是**同一个字符串**，不会出现导出的和屏幕上不一样。
3. **导航用 `transform: translate() scale()`，不用原生滚动条**：只有这样才做得到
   「以鼠标位置为锚点缩放」（缩放后指针底下的内容不动）。代价是失去了滚动条，
   所以配了拖拽平移 + 边界保护（内容至少留 60px 在视口里）。

导出的 `.svg` 是**自包含单文件**：样式内联在 SVG 里，颜色用 `var(--vscode-*, 兜底色)`，
所以在 VS Code 里跟随主题、丢进浏览器也能看。

### 9.2 不看 VS Code 也能看图

```bash
npm run route:dump -- --svg                 # ⇒ engine/build/route-swimlane.svg
npm run route:dump -- --html                # ⇒ engine/build/route-swimlane.html（整页预览）
```

`--html` 会拿**真实页面**（真实 HTML 生成器 + 真实文案 + 真实前端脚本）去浏览器里跑，
而且刻意**不走内联**、而是用 `postMessage` 投递数据 —— 也就是完整走一遍面板的链路。
这是除按 F5 之外唯一能验证 Webview 的手段（这个项目已经因为「打开一片空白」踩过一次坑）。

## 10. 降噪：把「纯转发 / 小函数」折叠掉

demo 上从 main 出发是 13 步，但真正值得**按顺序读**的可能只有 11 步 —— 中间夹着
`setVerbose`（`{ config().verbose = verbose; }`）、`size`（`{ return items_.size(); }`）
这种一行 getter。它们不是「边」，是噪声：占着一个步号，只会把真正要读的那几步冲淡。

判定规则是**两条同时满足**（只满足一条都会误伤）：

| 条件 | 为什么 |
| --- | --- |
| 函数体 ≤ 3 行 | 用**函数体行数**而不是「定义行号 − 签名行号」：多行签名会让后者虚高，把真函数误判成小的 |
| 只调用一处（≤1 个被调函数） | 只调一处的才是 getter / 纯转发；调两处以上的是在干活 |

第二条正是 demo 里的反例：`Engine::describe` 只有 3 行，但它调了 `join` / `split` 两处，
所以**必须留下** —— 折叠它等于把一条阅读线索藏起来。测试里有一条专门盯着这个反例。

### 10.1 折叠不是静默删除

这是这类功能最容易犯的错：用户看到 `main` 下面没有 `setVerbose`，会以为工具漏了这处调用。
所以引擎把被折叠的名字**挂到最近的那个保留祖先**上（`RouteStep.skipped`），
`skippedCount` 一并回报，界面分两处如实展示：

- 视图顶部那一行：`已折叠 N 个琐碎步骤（纯转发 / 小函数）`
- 那一步的 tooltip：`函数体 6 行` / `已折叠：setVerbose`（后者供你判断要不要单独去看它）

**不做成子节点是故意的**：被折叠的多半本来就挂在这一步下面（对 getter 来说，
最近的保留祖先几乎就是它的调用者），做成子节点等于原地不动、白多一层缩进 ——
那样折叠就完全失去意义了。

`skipTrivial` 是个**显式开关**（引擎默认 `false`，插件默认开着），关掉就回到 13 步原始清单：

```bash
npm run route:dump                 # 原始：13 步
npm run route:dump -- --trim       # 降噪：11 步，被折叠的名字标在各自的父步骤后面
```

```
 1 main · <6行>；src/main.cpp:6〔跳过：setVerbose〕
 4     run · <6行>；src/core/engine.cpp:27〔跳过：size〕
```

### 10.2 顺带修掉的一个定位 bug

做降噪要判断「这一步有没有函数体」，于是发现 `func:demo::setVerbose` 的位置是
**`src/main.cpp:9`（调用点）**而不是 `src/util/logger.cpp:14`（定义）。
根因在 `engine/src/session.cpp` 的符号合并：

```cpp
n.declaration = n.declaration && d.declaration;   // ← 先改了
if (n.declaration && !d.declaration) { ……把位置搬到定义处…… }   // ← 条件恒为假
```

「定义比头文件声明（甚至比调用点）晚出现」的符号，位置就永远停在第一次见到的地方。
改成先把旧值存下来再判断，并连 `module` 一起搬（否则会出现「文件在 `src/util/`、
模块却算 `src`」）。影响面很直接：点一步跳到的应该是**函数体**，而不是声明或调用点。
现在有断言盯着它（`test-rpc.mjs`：`setVerbose → src/util/logger.cpp:14`）。

> 这个 bug 是**降噪把它顺出来的**：一个位置在调用点、却有 1 行函数体的符号，
> 本身就是自相矛盾的。

## 12. 在 VS Code 里怎么用

侧边栏 → **DepScaner → 阅读路线**（或「操作 → 阅读路线（从 main 开始）」）。

| 操作 | 效果 |
| --- | --- |
| 点任意一步 | 跳到源码对应位置 |
| 标题栏 `$(arrow-both)` | 广度优先 ↔ 深度优先 |
| 标题栏 `$(file-code)` | 文件级 ↔ 函数级 |
| 标题栏 `$(filter)` | 降噪：折叠 / 展开「纯转发 / 小函数」（默认折叠，视图顶部会报折叠了几个） |
| 标题栏 `$(layers)` | 层视图：先给「第 N 层」摘要，一层太大就分页（见 §4.1） |
| 标题栏 `$(list-ordered)` | 重新生成 |
| 标题栏 `$(graph)` | 打开**泳道图**（同一个起点、同一批纠偏） |
| 标题栏 `$(target)` | 起点改成**光标所在的函数**（编辑器右键里也有「从光标处开始读」） |
| 标题栏 `$(home)` | 起点回到 main（只在你改过起点时出现） |
| 库项目：视图直接列出**起点候选** | 没有 main 时不用先找光标：点一行就从公开接口起头（§2.1） |
| 展开 ⚠ 步骤 → **候选** | 换一个同名定义 / 点「当前」撤回纠偏 |

泳道图面板里：**按住左键拖拽平移**、**滚轮以鼠标位置为锚点缩放**（指针底下那一步不会跑掉），
也可以 `−` / `+`（键盘 `+` `-`）、适应宽度（`f`）、原始大小（`0`）、导出 SVG、⟳ 重新生成。
点圆点直接跳源码；拖拽超过 4px 就当作平移，不会误跳。
重新生成时**不会**把你调好的视图打回去（只有换语言重建页面才会）。

> 导航手感刻意与依赖图面板一致（同样是滚轮 1.12 倍、同样是拖拽平移）——
> 同一个插件里两张图两种操作方式，那才叫不正常。
> 平移还带边界保护：不管怎么拖，内容至少留 60px 在视口里。
