# 07 · 阅读路线（Reading Route）

> 打开一个大项目，真正的问题不是「有哪些依赖」，而是**从哪读起、按什么顺序读**。
> 这一篇讲 DepScan 怎么回答这个问题。

---

## 1. 它和另外三张图的区别

| | 回答的问题 | 数据形态 | 渲染方式 |
| --- | --- | --- | --- |
| 文件依赖图 | 这个文件和谁有关？ | 无序子图 | 力导向图 |
| 符号子图 | 这个函数和谁有关？ | 无序子图 | 力导向图 |
| 全局架构图 | 项目分成几块？ | 按目录聚合 | 力导向图 |
| **阅读路线** | **先读什么、再读什么？** | **有序序列** | **有轴的列表 / 泳道** |

关键差别在最后一行：**前三个的核心信息是「关系」，路线的核心信息是「顺序」**。

力导向图的本质是无序的 —— 它为了减少连线交叉会把节点到处甩。用力导向图渲染「阅读顺序」，
等于把最重要的信息抹掉。所以阅读路线**不能**做成第四张力导向图，它需要一根轴。

---

## 2. 起点：main

路线的默认起点是程序入口，按顺序尝试：

```
main → wmain → WinMain → wWinMain → DllMain → mainCRTStartup → wmainCRTStartup
```

优先取**项目内有真实定义**的那个（跳过头文件里的声明和项目外的符号）。

> 库项目没有 `main` 怎么办？**从光标处开始读**（编辑器右键 / 侧边栏「操作」/ 标题栏
> `$(target)`）：引擎把 `(文件, 行号)` 换算成「该处所属的函数」，再拿它当起点。
> 界面上的「起点回到 main」可以随时撤销（只在真改过时出现）。
> 底层是两个接口：`nodeAt`（光标 → 节点）与 `route` 的 `from`（任意节点 id 都能当起点）。

---

## 3. 两个策略

调用图不是线性的：`main` 调 A、B、C，A 又调 D。所以「顺序」需要**一个遍历策略**来定义。

| 策略 | 走向 | 适合 |
| --- | --- | --- |
| **`bfs`（默认）** | 先读完 main 直接调用的，再进下一层 | **第一次读一个大项目** —— 先看骨架，再钻细节 |
| **`dfs`** | 跟着一条调用链一直走到深处，再回溯 | **追一条具体流程** —— 「这个请求到底经过了哪些函数」 |

**子节点的顺序按调用点的行号排**，所以阅读顺序跟随源码本身的书写顺序，而不是随机的图遍历顺序。
行号相同时按名字排 —— 这保证了**同样参数下路线完全可复现**，测试才能打靶断言。

---

## 4. 两个粒度

同一个功能，两个视角：

| 粒度 | 参数 | 效果 |
| --- | --- | --- |
| **函数级** | `groupByFile: false`（默认） | 每一步是一个函数 |
| **文件级** | `groupByFile: true` | 每个文件只保留**首次进入**的那一步 |

文件级模式下，被折叠掉的中间步骤不会让父节点悬空 —— 每个保留下来的步骤会被接到
**最近的、还被保留的祖先**上，所以缩进结构始终完整。

所以在 demo 上：函数级 13 步，文件级 8 步。

---

## 5. 参数

```jsonc
{
  "from": "",             // 起点节点 id；留空 = 自动找 main
  "strategy": "bfs",      // bfs（默认）| dfs
  "maxSteps": 200,        // 步数上限
  "maxDepth": 6,          // 跳数上限
  "projectOnly": true,    // 不进入项目外 / 未解析符号
  "groupByFile": false,   // 每个文件只保留首次进入
  "kinds": ["calls"],     // 参与遍历的边类型
  "overrides": {}         // 人工纠偏：{"<父节点 id>|<简单名>": "<改用的节点 id>"}
}
```

`overrides` 的 key 用**节点 id**而不是步号，是因为**步号会随纠偏本身变化** ——
在 `#5` 下换了一个候选，后面所有步号都可能移位，用步号做 key 的纠偏会在第二次应用时指错地方。
节点 id 在任何一次运行里都是同一个。

分隔符 `|` 是引擎与插件的硬约定（`engine/src/route.cpp` 的 `applyOverrides` 与
`src/views/routeTreeModel.ts` 的 `overrideKey`），两边都各有一条断言钉着。

**`projectOnly` 默认开着是有原因的**：真实项目里从 `main` 往下走一层就会撞上
`printf`、`std::vector::push_back`、平台 API。不挡掉的话，第 3 步开始就全是无关节点。
关掉之后这些外部符号会以 `<外部>` 聚合节点出现。

另一个接口：

```jsonc
// nodeAt：光标位置 → 该处所属的函数（「从光标处开始读」用的就是它）
{ "method": "nodeAt", "params": { "file": "src/core/engine.cpp", "line": 29 } }
// → { "id": "func:demo::Engine::run", "name": "run", "file": "src/core/engine.cpp", "line": 27, ... }
```

它取的是**同文件中行号 ≤ 光标行的最后一个函数定义**，而不是「最近的任意符号」——
读代码时的直觉是「我在这个函数里」。光标上方没有函数时才退回其他符号，最后退回文件节点。

## 6. 返回结构

```jsonc
{
  "from": "func:main",
  "steps": [
    { "order": 1, "parent": 0, "depth": 0, "newFile": true,  "ambiguous": false,
      "candidateTotal": 0,
      "id": "func:main", "name": "main", "file": "src/main.cpp", "line": 6,
      "kind": "function", "precision": "approximate", "external": false }
  ],
  "truncated": false,      // 是否因为 maxSteps / maxDepth 被截断
  "frontierNodes": 0,      // 还没展开的节点数
  "frontierFiles": 0,      // 还没展开的节点涉及多少个文件
  "maxReachedDepth": 3
}
```

- `order` 就是**阅读顺序**（1-based）
- `parent` 指向父步骤的 `order`，0 表示起点 —— UI 用它做缩进和连线
- `newFile` 是「首次进入该文件」标记
- `candidateTotal` 是**别的同名定义的数量**（不含自己）；> 0 时还会多一个 `candidates` 数组，
  每项带 `id / name / file / line / declaration`，最多列 20 个（`candidateTotal` 仍是真实总数）：

```jsonc
{ "order": 10, "name": "describe", "ambiguous": true, "candidateTotal": 1,
  "candidates": [ { "id": "func:demo::Engine::describe", "name": "describe",
                     "file": "src/core/engine.cpp", "line": 23, "declaration": false } ] }
```

> 候选**不含自己**：前端把「当前用的那一个」自己拼出来放到列表最上面（带勾），
> 点它就是撤回纠偏。否则用户会遇到「选错了却回不去」。

- 折叠（`groupByFile`）时候选信息跟着保留 —— 折叠只改结构，不改「这一步可能是错的」这个事实。

## 7. 诚实标注：路线不是「精确调用栈」

无 `compile_commands.json` 时，**调用边是按名字消解的**。普通依赖图错一条边只是多一条线，
但**顺序图错一条边，后面整条路径都是错的** —— 所以这里的可信度必须显式暴露。

`ambiguous: true` 的判定：**这个名字在项目里还有别的定义**（`candidateTotal > 0`）。

> 一开始我把它定义成「同一个父节点下有 ≥2 个同名子节点」。那是错的：
> 同一个函数下连着调两个同名函数在真实代码里几乎不会发生，而**按名字消解真正会出错的场景
> 恰恰相反** —— 图里别处还有个同名函数，消解挑错了那一个，于是**父节点下只有一个同名子节点**，
> 旧定义什么都不会报。把判定改成「全局同名定义」后，候选集也顺手拿到了：
> 可以直接列出来让用户自己选（demo 上 `describe` 命中了这个情况）。

判定只收**定义**、不收声明：`class Engine { void run(); };` 的声明不是「读代码要去的另一处」，
收进来会让每个成员函数都变成「有候选」，把信号淹掉。

### 7.1 纠偏：让用户改，而不是替用户猜

候选不只是显示，还能**直接改**：

```jsonc
// 让「Engine::run 里那句 describe()」改走 Base::describe
{ "method": "route", "params": { "from": "",
  "overrides": { "func:demo::Engine::run|describe": "func:demo::Base::describe" } } }
```

三条实现约定（都有断言钉着，见 §8）：

1. **key 用 `<父节点 id>|<简单名>`，不用步号**（理由见 §5）；
2. 选中的节点**即使原本不是该父节点的子节点也照走** —— 图里解析到了别的同名函数，
   这正是纠偏要修的东西；行号沿用原调用点，所以排序与遍历策略的行为完全不变；
3. 传空 `overrides` 与不传的结果**逐字节一致** —— 纠偏必须可撤销。

> 这是「近似精度」在这条功能上最直接的代价，写在这里而不是藏在实现里。

## 8. 验收标准（打靶测试）

不给「好不好看」下断言，只给「顺序对不对」下断言。`scripts/test-rpc.mjs` 里的实测：

```
自动识别程序入口：func:main
路线生成 13 步
第 1 步是起点且没有父节点（main）
打靶：main → Application::start(#3) → Engine::run(#5) → Registry::add(#8)
projectOnly 生效：路线里不含项目外符号
每一步都带符号名与文件位置（可点击跳转）
按文件折叠：13 步 → 8 步
折叠后每一步都是「首次进入某文件」
折叠后仍然只有一个根
maxSteps 截断生效：3 步，未展开 3 个节点 / 3 个文件
同样参数下路线完全确定（可复现，测试才能打靶）
```

V2 新增的断言：

```
同名定义候选：describe 另有 1 处定义
ambiguous 与候选列表一致（不会出现「标了黄却无候选可选」）
候选里不含它自己 / 候选都带 id / 同名 / 文件位置
candidateTotal(1) ≥ 列出的候选数(1)，且列出的不超过 20
纠偏生效：run 下的 describe 改走 src/core/engine.cpp:23（同名兄弟由 2 个收敛为 1 个）
纠偏后 src/core/base.h:25 不再是 run 的子节点（原边被换掉）
空 overrides 与不传 overrides 结果一致（纠偏可撤销）
光标定位：src/main.cpp:7 → main
光标定位：src/core/engine.cpp:29 → run（取所在函数，不是最近的任意符号）
从光标处出发：起点是 run 而不是 main
```

### 8.1 界面结构也能断言（`scripts/test-route-tree.mjs`）

TreeView 的真实渲染只能在有 UI 的扩展宿主里肉眼看，而肉眼看不出
「有候选的步骤忘了可展开」这类错 —— 候选那一行会静静地点不出来（写这版时确实先犯过一次）。

所以把结构抽成纯函数 `src/views/routeTreeModel.ts`（不 import vscode），用固定数据喂它：

```
根层 = 1 个根步骤 + 1 条尾行
size 没有子步骤但有候选 —— 仍然必须可展开（否则候选点不出来）
候选分组挂在「有同名定义的那一步」下面，而不是挂在它的父节点上
trim 没有子步骤也没有候选 —— 不可展开（不显示展开箭头）
候选分组 = 1 个「当前」 + 2 个候选
点「当前」= 撤回纠偏（reset），不是又选一次它自己
args 里带的是父节点 id + 简单名，与引擎 applyOverrides 的 key 对齐
起点的候选 parentId 为空 —— 命令据此把候选当成「换个起点」而不是纠偏
overrideKey 的分隔符与引擎一致
折叠（文件级）后仍然只有一个根 —— 悬空的父节点不会冒出来
```

### 8.2 不看 UI 也能核对路线：`npm run route:dump`

```bash
npm run route:dump                                    # demo，从自动识别的入口出发
npm run route:dump -- --dfs --files                    # 深度优先 + 文件级
npm run route:dump -- --file src/core/engine.cpp --line 29   # 从「光标」处出发
```

输出就是 UI 里那棵树（含 ⚠ 与候选），并附一行「多少步存在同名定义」。
文档里贴的清单就是这么来的 —— 改了消解逻辑之后，`git diff` 能直接看出顺序变没变。

`samples/demo` 上从 `main` 出发的真实路线：

```
起点：func:main
策略：bfs　粒度：函数级　步数：13　最深层数：4

 1 main ·       src/main.cpp:6
 2   setVerbose src/main.cpp:9
 3   start ·    src/app/application.cpp:9
 4     config · include/demo/config.h:24
 5     run ·    src/core/engine.cpp:27
 7       trim · src/util/string_utils.cpp:7
 8       add ·  src/core/registry.cpp:8
 9       describe       src/core/engine.cpp:23
12         join src/util/string_utils.cpp:30
13         split        src/util/string_utils.cpp:15
10       describe ⚠     src/core/base.h:25
            └ 候选：func:demo::Engine::describe（src/core/engine.cpp:23）
11       size   src/core/registry.cpp:16
 6     render · src/ui/panel.cpp:13

路线已完整生成
同名定义候选：1 / 13 步存在「可能是错边」的情况
```

读起来就是：**main 起手 → 启动 Application → 跑 Engine → 往 Registry 里加东西 → Registry 去调 Panel 渲染**。
这正是「按顺序读一个项目」需要的那条线。

> 注意树里的行不是步号顺序（`#9 → #12 → #13 → #10`）：树按**调用关系**排，
> 步号是按**广度优先的阅读顺序**排。想看两者一致就切 `--dfs`。

## 10. 在 VS Code 里怎么用

侧边栏 → **DepScan → 阅读路线**（或「操作 → 阅读路线（从 main 开始）」）。

| 操作 | 效果 |
| --- | --- |
| 点任意一步 | 跳到源码对应位置 |
| 标题栏 `$(arrow-both)` | 广度优先 ↔ 深度优先 |
| 标题栏 `$(file-code)` | 文件级 ↔ 函数级 |
| 标题栏 `$(list-ordered)` | 重新生成 |
| 标题栏 `$(target)` | 起点改成**光标所在的函数**（编辑器右键里也有「从光标处开始读」） |
| 标题栏 `$(home)` | 起点回到 main（只在你改过起点时出现） |
| 展开 ⚠ 步骤 → **候选** | 换一个同名定义 / 点「当前」撤回纠偏 |

界面选择 TreeView 而不是再开一个画布，是权衡后的结果：这个功能的核心是**顺序**，
而 TreeView 天然给了「有序 + 可缩进 + 键盘上下走 + 点一下跳源码」四件事。
泳道图（V2）才需要回到画布，因为「文件之间的流向」是关系而不是顺序。

视图顶部（`TreeView.message`）显示起点、精度提示与「多少步存在同名定义」—— 不占用节点行。

干预是**会话内**的：起点与纠偏不会写进磁盘，重启 VS Code 后回到「自动从 main 开始、按名字消解」。
