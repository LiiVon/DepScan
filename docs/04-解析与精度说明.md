# 04 · 解析与精度说明

> 工具最大的风险不是不够强，而是**让你误以为它是对的**。
> 这一篇讲清楚：什么情况下 DepScan 的结果可信到什么程度。

---

## 1. 三级精度

整体精度由引擎上报，取值为下面三者之一：

| 整体精度 | 触发条件 | 含义 | 在 UI 上 |
| --- | --- | --- | --- |
| **精确 (exact)** | 引擎链接了 libclang | 五类依赖都是语义级结果（重载决议、模板实例化、宏展开后的真实包含） | 状态栏/索引视图显示「精确」 |
| **部分精确 (partial)** | 找到并解析了 `compile_commands.json`，但未链 libclang | `includes` 与 `links` 精确；`calls / inherits / uses / refs` 仍为结构级 | 状态栏/索引视图显示「部分精确」 |
| **近似 (approx)** | 两者都没有 | 全部依赖都是结构级近似 | 状态栏/索引视图显示「近似」 |

**关键点：精度是“逐节点 / 逐边”标注的，不是全局开关。**
同一个项目里，某些文件在编译数据库中有条目（`-I` 命中 → 精确），另一些没有（后缀匹配 → 近似），
UI 会同时显示两种：实线边 = 精确，虚线边 = 近似。

状态栏、「索引状态」视图、侧边栏「操作 → 重新索引」右侧的短标签显示的是**整体精度**；
具体某条边是否精确，看边的虚实与表格里的标记。

### 1.1 编译数据库去哪里找

引擎按下面的顺序查找（与扩展侧 `src/index/compileDb.ts` 严格一致）：

1. `<root>/compile_commands.json`
2. `<root>/build/`、`<root>/out/`
3. `<root>/cmake-build-debug/`、`<root>/cmake-build-release/`
4. `<root>/build/Release/`、`<root>/build/Debug/`
5. 兜底：从根目录**有限深度递归**（深层目录、`.git`、`node_modules`、`_deps` 会被跳过）

CMake 预设（`CMakePresets.json`）常把它放在 `out/build/<预设名>/` 下，第 5 步会兜住。

想直接看到“到底找没找到、找过哪里”，运行命令面板的 **DepScan: 为什么是近似？（精度诊断）**。

## 2. 五类依赖的语义与限制

### 2.1 `includes` —— 文件包含

**识别什么**

- `#include "a.h"` 与 `#include <a.h>`（区分本地引用与系统引用）
- 包含路径搜索顺序：先相对被包含文件所在目录 → 再 `-I` / `-isystem` 路径 → 最后按文件名后缀唯一匹配
- `#include` 的**宏展开**：`#define MY_HDR "real.h"` + `#include MY_HDR` → 解析为 `real.h`（支持多级别名）

**限制**

- 条件编译（`#ifdef`）**不做预处理**：所有分支里的 `#include` 都会被记录。对"看懂依赖"通常有益（更全），但对"精确的编译单元依赖"会有多余边。
- 系统头文件（如 `<vector>`）若无编译数据库，通常只能按名字在项目内匹配；匹配不到就标记为「未解析」。

**精度来源**

- 走「相对目录」或 `-I` 命中 → **精确**
- 靠文件名后缀唯一匹配 → **近似**

### 2.2 `calls` —— 函数调用图

**识别什么**

- 函数体内部的 `name(` 形式调用，含 `A::B::c` 限定名链
- 成员函数（含 `this->` / `.` / `->` 形式）
- 返回类型中的调用（`Foo bar() { return baz(); }`）

**限制（重点）**

- **按名字消解**：`count(1)` 会匹配项目内所有名为 `count` 的符号
  - 唯一命中 → 直接连边
  - 多个命中（重载）→ **优先同文件**，其余按确定性顺序全部连边（≤3 个）；>3 个候选时聚合为一个「未解析」外部节点，避免爆图
  - 无命中 → 若开启「显示项目外符号」则建外部节点，否则忽略
- **代价在「顺序」上会被放大**：依赖图错一条边只是少一条线，
  但[阅读路线](07-阅读路线.md)错一条边会让它**后面整条阅读顺序都是错的**。
  所以路线视图会把「这个名字在项目里还有别的定义」的步骤标 ⚠，
  并把候选定义列出来让你自己核对 / 切换（你改的选择会作为 `overrides` 传回引擎）。
  真正的解法仍然是给一个 `compile_commands.json`。
- 函数指针、`std::function`、虚函数动态派发**无法静态确定**，只按静态类型连边
- 模板函数只按**写出来的那个名字**连边，不展开实例化
- Lambda 内的调用归属到外层函数

**精度**：始终为**近似**（除非将来启用 libclang 语义分析，见第 4 节）。

### 2.3 `inherits` / `uses` —— 继承与类型依赖

**识别什么**

- `class A : public B, protected C` → `A → B`、`A → C` 的 `inherits` 边
- 类体的成员声明类型 → `uses` 边（`std::vector<Foo> m_items` 会提取主类型 `Foo`；`ns::Bar` 提取 `Bar`）
- 继承列表中的模板参数会取主类型（`Base<T>` → `Base`）

**限制**

- 不做 typedef / using 别名展开
- 不做模板实参递归分析（`std::map<K, V>` 只取 `K`）
- 虚继承（`virtual public`）语法上能识别，但语义上与普通继承不做区分

**精度**：近似。

### 2.4 `refs` —— 符号交叉引用

**识别什么**

- `#define` 定义的宏 → 宏节点
- 形如 `ALL_CAPS_WITH_UNDERSCORE` 的标识符使用 → 宏引用边（宏调用的启发式）
- 全局 / 命名空间作用域的变量定义 → 变量节点

**限制**

- 全大写标识符可能是枚举常量或常量变量，会被当作宏引用（有噪声）
- 局部变量**不建节点**（避免图爆炸）
- 同一文件内同一宏名只记录一次引用（去重）

**精度**：近似。

### 2.5 `links` —— 链接 / 构建依赖

**识别什么**（解析 CMake）

- `add_executable` / `add_library` → **构建目标**节点
- `target_link_libraries` → `目标 → 被链接库/目标` 的 `links` 边
- `add_executable/add_library` 的源文件列表 → `目标 → 源文件` 的 `links` 边

**限制**

- 目前**只解析 CMake**（`CMakeLists.txt`，跳过 `build/`、`_deps/`）
- 含变量展开的写法（`${SRC_LIST}`、`$<TARGET_NAME:...>`）会被跳过（无法静态求值）
- 非 CMake 构建系统（Makefile / Bazel / qmake）**不解析构建元数据**，此时不会有 `links` 边 —— 但仍可通过 `compile_commands.json` 获得 include / 调用等信息

**精度**：**精确**（来源就是构建脚本本身，属于"声明的真相"）。

### 2.6 公开面（`apiHeader`）—— 一个标记，不是第六类依赖

节点上会多两个字段：`apiHeader` / `apiLine`，指的是**这个符号的声明落在哪个公开头文件里**。
空 = 不是公开接口。它不产生边，只是把「别人能用什么」标出来：

- 阅读路线：公开接口那一步换成接口图标，悬停显示声明位置
- 依赖图：树行与表格行多一个 `公开` 角标，详情里列一行；画布上不画（大项目里公开面是大多数，画上去就是噪声）
- 起点候选（`entries`）：库项目按它挑「从哪读起」

**判定规则（重要，因为它是个约定）**：路径以 `include/`、`inc/`、`public/`、`api/` 开头的文件
算公开面。这是安装规则最常见的写法（`install(DIRECTORY include/ ...)`），也是这个功能**唯一**
可核对的信号 —— 没有编译数据库时：

- `__declspec(dllexport)` / `__attribute__((visibility))` 这类导出属性**不解析**
- CMake 的 `PUBLIC` / `PRIVATE` / `INTERFACE` 关键字也只是**字符串**（不建目标模型）
- 因此这是一个**目录约定**，不是语法事实：头文件都在 `src/` 里的项目就没有公开面

好处是零配置、可预测、看一眼目录就能核对；代价是它会被目录命名糊弄（把内部头文件放进
`include/` 就会被当成公开面）。真要做到语法级判定，得靠 libclang 那一档。

## 3. 精度一览表

| 依赖类型 | 有 compile_commands（未链 libclang） | 无 compile_commands |
| --- | --- | --- |
| `includes` | 精确（`-I` 命中）/ 近似（后缀匹配） | 近似 |
| `calls` | 近似 | 近似 |
| `inherits` | 近似 | 近似 |
| `uses` | 近似 | 近似 |
| `refs` | 近似 | 近似 |
| `links` | 精确（来自 CMake） | 精确（来自 CMake） |

所有精度标注都是**对结果负责**的：引擎宁可把一条边标成近似，也不会把没把握的结果说成精确。

## 4. 关于 libclang / tree-sitter

需求里提到了基于 libclang 的精确语义分析与 tree-sitter fallback。当前实现的选择与现状：

- **默认解析器**：内置 C++ 词法 + 结构解析器。它零外部依赖、跨三平台、启动即用，代价是上面列出的近似性。
- **libclang 精确路径**：CMake 提供了 `-DDEPS_USE_LIBCLANG=ON` 开关。本机 `find_package(Clang)` 成功时会链接 `libclang`，由 `engine/src/clang_analyzer.cpp` 提供精确的 AST 级分析（重载决议、模板实例化、宏展开后的真实包含）。
  - 该路径**默认关闭**：因为要求用户机器上有 LLVM，与「下载即用」的产品目标冲突。
  - 开启后引擎会在 `ping` / `stats` 里上报 `libclangAvailable: true`，UI 的精度标识随之提升。
- **tree-sitter**：未引入。原因是在本项目的实际权衡里，内置解析器已经覆盖了「结构级」这一档位能提供的信息，再引入 tree-sitter 会增加三平台构建矩阵与 vsix 体积，收益有限。若你需要更强的语法级准确度，建议直接使用 libclang 路径。

> 这是一个**有意识的取舍**，写在这里是为了让你知道边界在哪，而不是让文档显得更完整。

## 5. FAQ

**Q：为什么图里有个灰色虚线框、名字叫 `std::vector` 之类的节点？**
那是「未解析」节点。说明这个符号在项目内找不到定义（属于标准库/第三方库）。打开工具栏的「显示项目外符号」才会出现。它的价值是让你看到"我依赖了哪些外部能力"，噪声大时关掉即可。

**Q：为什么我明明编译过了、也点了刷新，还是显示「近似」？**

按这个顺序排查（也可以直接运行 **DepScan: 为什么是近似？（精度诊断）**，它会一次性告诉你结论和下一步）：

1. **编译不等于生成了编译数据库。** `build/CMakeCache.txt`、`.vcxproj`、`.obj`、`.exe` 这些**都不算**，只有 `compile_commands.json` 算。

2. **【最常见的坑】CMake 的 Visual Studio 生成器根本不产出这个文件。**
   官方文档就写着：`CMAKE_EXPORT_COMPILE_COMMANDS` **只对 Makefile 与 Ninja 生成器生效**。
   而 CMake Tools 的默认 Kit 恰好就是 `Visual Studio ...` 生成器 —— 所以即使你加上开关、重新配置、重新构建，
   `build/` 目录里依旧永远不会出现 `compile_commands.json`。

   自判方法：打开你的 `build/` 目录
   - 有 `CMakeCache.txt` / `*.vcxproj` / `CMakeFiles/`，**但没有** `compile_commands.json` → 就是这个坑

   解法：换 **Ninja** 生成器（本机实测可行）：

   ```bat
   :: Windows + MSVC：先进入 VS 环境，再用 Ninja 配置
   "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
   cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
   cmake --build build
   ```

   在 VS Code 里不想敲命令：CMake Tools → **Select a Kit** 选带 Ninja 的 MSVC Kit，
   再在 `.vscode/settings.json` 里加 `{ "cmake.exportCompileCommands": true }`。

3. **位置不在查找范围内。** 见上面 1.1 节的查找顺序（会在深度 ≤ 4 的范围内递归找，所以 `engine/build-ninja/` 这种位置也会被找到）；
   如果生成物在更奇怪的地方（IDE 临时目录、绝对路径的 out-of-source build，或路径带空格），
   用 `depscan.compile.commandsPath` 显式指定绝对路径。

3. **它是刚生成的，而索引是更早做的。** 现在这种情况会**自动处理**：
   - 扩展会监听 `**/compile_commands.json`，一旦出现/变化，会防抖后自动全量重新索引；
   - 面板工具栏的 ⟳ 也不再只是「重新取一次子图」，它会先检查编译数据库是否比上次扫描更新，需要时先重扫；
   - 如果重启后发现结果仍旧，运行一次「重新索引」即可。

4. **缓存真的刷掉了吗？** 磁盘缓存现在带**配置指纹**（根目录 + 编译数据库路径/条目数/mtime + include 路径 + 宏 + 文件大小上限）。
   任何一项变化，旧缓存都会被丢弃并在日志里提示「编译数据库或编译参数已变化…已丢弃旧缓存并重新解析」。
   如果怀疑缓存有问题，用「清除缓存」后重新索引。

5. **显示的是「部分精确」而不是「精确」，这是正常的。** 没链接 libclang 时，call/继承/类型仍然只能做到结构级；
   要拿到五类全精确，需要 `-DDEPS_USE_LIBCLANG=ON` 的引擎构建（见第 4 节）。

**Q：为什么刷新之后精度变了、图也变了？**
说明编译数据库在两份索引之间发生了变化（新生成 / 重新配置 / 换了构建目录）。包含关系与链接边的集合会随之变化，这是预期行为，不是抖动。

**Q：明明改了代码，图没变？**
- 检查 `depscan.index.autoRebuildOnSave`（默认 true）
- 增量更新有 400ms 防抖；再等一秒或点工具栏 ⟳
- 如果正在全量索引，保存事件会被跳过

**Q：`main` 函数没出现在图里？**
`main` 只有在被调用或作为焦点时才有边。以 `src/main.cpp` 为焦点、`k ≥ 1` 即可看到它（文件与其内部符号之间是"包含"关系，会一起展开）。

**Q：为什么继承边只有一条，我明明有多个基类？**
检查基类是否写成了模板 / 别名 / 宏展开形式；当前实现只取「主类型名」，模板实参与别名的解析在近似精度下不保证完整。

**Q：同名的静态函数会导致错误的调用边吗？**
会。近似精度下按名字消解，同名符号会优先同文件匹配（这能消除大部分误报），但跨文件同名静态函数仍有误连可能。这类误报在读图时表现为"凭空多出一条调用边"。

**Q：为什么 `links` 边指向的库名和我 CMake 里写的不完全一致？**
`target_link_libraries` 里的名字会原样保留（去掉 `PRIVATE/PUBLIC/INTERFACE` 等修饰词）。如果是 `target_namespaced::lib` 形式，命名空间会保留在名字里。

**Q：能分析 C 语言项目吗？**
可以。`.c` 与 `.h` 都在索引范围内，include / 调用 / 结构体 / 宏都能识别；只是 `class`/继承相关的能力在纯 C 项目里自然不会被触发。

**Q：索引失败，日志里写 `No mapping for the Unicode character exists in the target multi-byte code page`？**
这是**路径里的非 ASCII 字符**撞上了 Windows 的「进程 ANSI 代码页」（新版已修，请更新扩展）。

- 现象：`npm test` 全绿、自造样例（ASCII 路径）也全绿，一放到真实项目上就在「1/5 发现文件」阶段直接失败。
- 原因：引擎内部所有路径都是 UTF-8，而 MSVC 的 `std::filesystem::path` / `std::ifstream`
  在窄字符串与宽字符互转时用的是**进程 ANSI 代码页**（中文机器 = 936/GBK）。
  项目里只要有**一个**名字不是合法 GBK 字节序列（emoji、日文、韩文、部分中文组合……），
  转换就会失败：轻则 `fs::exists` / `ifstream` 静默读不到文件，重则直接抛上面那句异常。
- 修法（两处，缺一不可）：① 给 exe 链接一份
  [`activeCodePage=UTF-8` 清单](../engine/resources/utf8-app.manifest)（Win10 1903+）；
  ② 代码里所有路径转换都过 `util::toFsPath` / `util::fromFsPath`，显式指定 `CP_UTF8`，
  不依赖代码页、也不依赖系统版本。
- 回归测试：`npm test` 里的 `test:unicode`（`scripts/test-unicode-paths.mjs`）会造一个
  「带空格的根目录 + `中文目录/` + `emoji-😀/`」的样例工程，断言能扫出来、路径原样是 UTF-8、
  include 与调用边都解析成功。改引擎的路径处理时它会立刻报警。
- 如果你手里的版本还会报这个错，先跑一次 `DepScan: 重建索引（全量）`；
  仍旧失败就把项目路径里那个特殊字符发我（或者先用 `--trace` 定位到具体文件）。

**Q：项目路径很长（超过 260 字符）会有问题吗？**
引擎本身没开 `longPathAware`，能否支持取决于操作系统的
`LongPathsEnabled` 开关与 VS Code 侧的行为；这是已知边界，遇到再说。

**Q：索引很慢 / 内存很高怎么办？**
见 [05-性能与配置参考](05-性能与配置参考.md) 的调优章节。
